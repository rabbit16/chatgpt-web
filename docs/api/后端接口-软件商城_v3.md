# 软件商城改造 · 后端接口契约 **v3（响应格式 / source / category 修正版）**

> 面向读者：站长（编程小白，按本文照做即可）、后端工程师（照表实现）。
> 更新：2026-10-25 · **v3 修订：按站长验收 bug + 真实接口实测，补齐三处契约缺口** —— ① 响应格式不统一（`code` 是字符串 `"0"`、数据在**顶层 `list`**，没有 `data` 包裹）；② `source` 字段**完全没返回**（直接导致商城「官方软件」页签永远为空）；③ `category_id` 的「存」与「筛」需后端逐条确认。
> **版本关系**：v1 见 [`后端接口-软件商城_v1.md`](后端接口-软件商城_v1.md)、v2 见 [`后端接口-软件商城_v2.md`](后端接口-软件商城_v2.md)（两版正文均未改，留作历史）。**v3 = v2 全文 + 本次 6 项修正**；章节编号一律不重排，只**新增** `3.0.1`、`3.4.1`、`3.13`、`8.4` 四节，并在既有表格里补行。
> **v2 的多平台修订依然有效**：管理员直传从「单平台」改为「多平台（复选）」，见 3.2、3.12、5.5。
>
> **本版依据站长需求原话**：
> ①（v1）「软件商城里把当前已有的余额兔软件删掉，新增官方软件和用户上传软件，官方软件是我们有管理权限的人从后台上传的，因此需要在后台的软件上传页面增加接口，可供管理员直接上传自己写的软件，用户上传的这个按钮继续保留，需要后台审核通过才可正式上传。」
> ②（v2）「平台只能单个选择某个平台，但我上传链接的话就是三个平台同时都能在一个链接下载」「最好能复选」「派专家进行相应设计和修改，保证前后端的同步考虑」
> ③（v3，站长验收 bug）「后台管理员直接上传的软件出现在了『接入指南』里，没出现在软件商城的官方软件列表。接入指南里只应该对应 AI(Agent) 那个分类，因为那是用来指引客户下载 AI 工具台的。」
>
> **v3 的事实来源（2026-10-25 直连线上 `https://www.rabbitj.top/apiAI` 实测，非推测）**：`POST /user/software/list`（body `{"page":1,"page_num":20}`）返回 4 条记录（id 1–4）、13 个字段；`POST /user/software/category/list` 返回 2 条分类；`category_id` / `source` / `keyword` / 分页 / `detail` 五个行为已逐个实测，结论见 **3.0.1**（响应格式）与 **3.4.1**（筛选行为）。**凡本文标注「实测」的都是这次真跑出来的；标注「待后端确认」的，我没有依据，不猜。**
>
> **⚠️ 先纠正三条与站长口述不一致的地方（有实测数据，请以本文为准后再安排后端）**：
> 1. **`category_id` 筛选其实是生效的**，不是「未生效」。实测 `category_id=1` 只返回 id 1/2/3（3 条，全属 AI(Agent)），`category_id=3` 只返回 id=4（余额兔，效率软件）。**真正的问题是「写入时存错了分类」，不是「查询时筛不动」**——详见 3.4.1 与 3.13。
> 2. **接入指南并不是「显示了官方软件」，而是「把商城全部软件都显示了」**：前端取数原来没带 `category_id`。这条**前端已修**（改成按分类名匹配 AI(Agent)，见 3.13），但**后端仍需确认分类 id 稳定性**。
> 3. **响应格式的后果要说准**：`code:"0"` + 无 `data` 包裹，**不会**让前端进「本地模式」（前端响应层会重包成 `{code:0,data:原body}`，见 3.0.1 实测说明），真正后果是**顶层业务错误码被抹平、`message`/`codeMsg` 语义丢失、`total`/`page` 取不到**。这与「接口失败」是两件事，本文按实测写。
>
> 前端对应代码（并行实现，契约已按本文固化）：`chatgpt-web/src/pages/projects/index.tsx`（商城）、`src/pages/admin/software/index.tsx`（后台软件下载页）、`src/pages/admin/projects/index.tsx`（现有审核页）、`src/request/api.ts`、`src/request/projects.ts`、`src/request/software.ts`。
> 本文**只写契约，不涉及改代码**；后端按本文实现后，前端不需要改调用方式即可切换。
>
> 生活化解释（第一次出现的术语都在这里说明，后文直接用）：
> - **契约**：前后端约好的「说话方式」，比如请求哪个地址、带哪些字段、出错回什么码。约好了两边各自写代码，就不会对不上。
> - **接口**：一个可以调用的地址，像餐厅点菜窗口，把菜名（参数）递进去，厨房（后端）做好端出来（返回数据）。
> - **官方 / 用户上传**：官方 = 我们自己人做的软件，直接摆上货架；用户上传 = 别人做的，先放仓库，我们检查过才摆上货架。
> - **审核**：管理员看一遍用户提交的东西，决定「通过」还是「打回重做」。
> - **幂等**：同一个请求重复发几次，结果和发一次一样（不会重复建两条记录、不会重复扣钱）。
> - **单平台 / 多平台**（v2 新增）：单平台 = 一个软件只有一个安装包，只能给一种系统用；多平台 = 一个软件挂了 Windows、macOS、Linux 三个安装包（或者三个平台共用同一个链接）。**v2 就是把「只能单选」改成「可以复选」。**
> - **主表 / 明细表**（v2 新增）：主表像「商品档案卡」，只记这个软件叫什么、谁做的；明细表像「商品规格表」，记每个系统各自用的包和链接。一个档案可以挂多条规格。
> - **响应包裹 / `data` 包裹**（v3 新增）：后端回话的「信封」。约定是信封上写 `code`（成功与否）、`message`（一句话说明），里面再套一层 `data`（真正的内容）。现在线上的信封**没有 `data` 这一层**，内容直接摊在信封上（顶层 `list`），这就是本版要统一的东西（3.0.1）。
> - **`source` 字段**（v3 新增，本版最关键的名词）：给每条软件盖的「产地章」，只有两个值 —— `official`（官方，我们自己人上传）和 `user`（用户上传）。**没有这个章，商城就分不清哪个该进「官方软件」页签、哪个进「用户上传」页签**，两个页签会一起错乱（3.4）。
> - **硬编码 id**（v3 新增）：把「1」这样的数字直接写死在代码里。像把「3 号柜」写进说明书，柜子一重排，说明书就全错。**分类 id 不要写死，按名字去查**（3.13）。
> - **回填（backfill）**（v3 新增）：老数据缺了新字段，用一条 SQL 统一补上。像给以前入库的旧档案统一补盖一个章（3.4.1 给 SQL）。

## 〇、一句话结论（先看这个）

1. **不新起一套接口**，在现有 `/user/admin/software/*`（后台软件下载页）和 `/user/software/list`（商城列表）上**加字段、加两个新接口**：管理员上传（upload）、官方创建（create 已存在）、用户提交（submit）、待审队列（review/list）、审核动作（review）。
2. **两条上架路径**：官方 `source=official`，管理员提交即上架（`status=1`，`review_status=approved`）；用户 `source=user`，提交后 `review_status=pending` + `status=0`，管理员通过才公开。
3. **余额兔从商城移除**：不再作为列表兜底假数据；`public/downloads/*.zip`、`public/covers/yuebao.svg` 保留在仓库里没关系，但**不作为后端数据源**，商城/后台都不再读取它。
4. **老数据迁移**：`software` 表已有记录的 `source` 一律默认 `official`，避免老软件突然从商城消失。
5. **旧文档关系**：`docs/后端接口-开源项目.md` 里的 `/open-source/*` 属于「软件商城」的**上一版方案**，被本文取代；建议保留只读、设下线日期（见第 1.3 节），**不立即删除**，防止前端并行改动期间两边打架。
6. **（v2 新增）管理员直传支持多平台复选，优先级一句话说完**：`create` / `update` / `submit` 三个写接口统一用 **`platforms` 数组**（一个元素 = 一个平台 + 一条链接）；**`platform`（单数）和 `platforms` 同时传时，以 `platforms` 为准，单数 `platform` 直接忽略**；只传 `platform` 不传 `platforms` 时，服务端按「单元素数组」处理——**新旧两种写法都能用，老前端不会坏**。支持范围 = `windows` / `macos` / `linux` 任意复选 1–3 个，**三个平台可以填同一条链接**（站长场景：GitHub Releases 页或网盘文件夹，一个链接三个平台都能下）。详见 3.2 与 3.12。

**（v3 新增）本次验收 bug 的三条结论，按这个顺序修最省事**：

| 序 | 要改什么 | 改成什么 | 谁改 | 改完站长的直观变化 |
|---|---|---|---|---|
| **1** | **`list` / `detail` / `review/list` 返回 `source`** | 每条记录**必须**带 `source`（`official`/`user`），并跑一次存量回填 SQL | 后端 | 商城「官方软件」页签**立刻有内容**，不再空白 |
| **2** | 响应格式统一 | `{code:0, data:{list,total,page}, message:"ok"}`；过渡期 `code` 允许是字符串 `"0"`（前端已兼容） | 后端 | 出错时能弹出后端真实的中文提示；分页总数准确 |
| **3** | `create` / `update` 是否真存 `category_id` | 存前端传的值，**不许静默改成默认分类** | 后端 | 站长选「AI(Agent)」上传，就真的落在 AI(Agent) 分类，不再跑偏 |

> 一句话：**第 1 条是站长这次看到的现象（官方页签空白）的根因，必须先修**；第 2、3 条不修也能用，但会让联调反复踩坑（详见 3.0.1、3.4.1）。

## 一、背景与改动范围

### 1.1 为什么要拆「官方」和「用户上传」两类

| 现状问题 | 说明（站长视角） |
|---|---|
| 商城和后台是两套东西 | 后台「软件下载」（`/user/admin/software/*`）能增删改、有分类和链接；商城前台（`/projects`）却走另一套 `/open-source/*`，还内置了一个「余额兔」假数据当兜底。两边数据不通：后台加了软件，商城看不到。 |
| 余额兔是写死的假数据 | 商城的第一张卡片不是从数据库来的，是前端代码里写死的（`FALLBACK_PROJECTS`）。接口一挂就显示余额兔，容易让人误以为后端有数据。 |
| 用户上传没有「谁提交的」 | 旧方案 `/open-source/*` 提交后进的是一张独立表，和后台软件管理不是同一份数据；管理员在「软件下载」页里看不到用户提交，要去另一个页面审。 |
| 官方软件和用户软件混在一起 | 商城分不清哪个是我们官方发的、哪个是用户传的，用户也不敢下。 |

**改完之后**：
- 后台「软件下载」页 = 唯一的软件数据源（官方 + 用户上传都在这里）。
- 后台新增两个能力：管理员**直接上传安装包**、管理员**审核用户提交**。
- 商城前台只认 `source` 字段：官方带「官方」标记、置顶；用户上传的只有审核通过的才出现。
- 余额兔下线，不再兜底。

### 1.2 改动范围一览

| 类型 | 接口 | 说明 |
|---|---|---|
| **新增** | `POST /user/admin/software/upload` | 管理员上传安装包/封面（multipart） |
| **扩展**（已存在） | `POST /user/admin/software/create` | 增加 `source`（服务端强制 official）、`version`、`changelog`；**v2：新增 `platforms[]` 多平台复选，`platform`（单数）降为兼容期可选（见 3.2）** |
| **扩展**（已存在） | `POST /user/admin/software/update` | 同上，另支持 `is_delete`；**v2：同样支持 `platforms[]` 与优先级规则（见 3.3）** |
| **扩展**（已存在） | `POST /user/software/list` | 新增 `source`、`keyword` 参数；返回项新增 `source/author_name/version/download_count/review_status`；**v2：返回项新增 `platforms[]`，单数 `platform`/`file_url` 降为「主平台摘要」（见 3.4）** |
| **新增（可选）** | `GET /user/software/detail?id=` | 详情页；未实现时前端从 list 降级取 |
| **新增** | `POST /user/software/submit` | 用户提交软件/新版本 |
| **新增** | `GET /user/software/my-submissions` | 用户看自己提交的审核状态 |
| **新增（可暂不实现）** | `POST /user/software/upload` | 用户上传安装包；不实现时前端只填网盘链接 |
| **新增** | `GET /user/admin/software/review/list` | 待审队列 |
| **新增** | `POST /user/admin/software/review` | 通过 / 驳回 |
| **下线** | `/open-source/*` | 旧方案，见 1.3 |

### 1.3 与旧文档 `docs/后端接口-开源项目.md` 的关系

| 旧接口 | 处理建议 | 原因 |
|---|---|---|
| `GET /open-source/projects` | **废弃**，由 `POST /user/software/list` 取代 | 商城数据统一走 software 表 |
| `GET /open-source/my-projects` | **废弃**，由 `GET /user/software/my-submissions` 取代 | 同上 |
| `POST /open-source/projects` | **废弃**，由 `POST /user/software/submit` 取代 | 字段名不同：旧 `releases[]` → 新 `platforms[]` |
| `POST /open-source/upload` | **废弃**，由 `POST /user/software/upload` 取代 | 换统一前缀与权限模型 |
| `GET /admin/open-source/projects` | **废弃**，由 `GET /user/admin/software/review/list` 取代 | 并入现有后台软件管理 |
| `POST /admin/open-source/review` | **废弃**，由 `POST /user/admin/software/review` 取代 | 同上 |

**下线策略（建议）**：

1. **兼容期（建议 ≥ 30 天）**：旧接口**保留可用**，后端内部改成读新表（`software` + `software_release`），返回结构保持旧格式。这样前端改到一半、用户还开着旧页面，也不会报错。
2. **标记废弃**：旧接口响应头加 `Deprecation: true`，并在 `data` 里加 `deprecated: true`（不影响旧前端解析）。
3. **下线日期**：建议 `2026-12-01` 之后返回 `410 Gone` + `{"code": 4410, "message": "该接口已下线，请使用 /user/software/list"}`。**具体日期请站长拍板**（见文末问题 1）。
4. **旧表怎么处理**：`open_source_project` / `open_source_release` 里已有的真实数据，在切换时**一次性迁进 `software` / `software_release`**（见第 7.3 节示例 SQL），迁完旧表转只读，不再写入。
5. 本文写完后，已在 `docs/后端接口-开源项目.md` 顶部加了一行「⚠️ 本文部分内容已被本文取代」的提示，**正文一字未改**，留作历史记录。

## 二、状态机

### 2.1 两个字段，别搞混

| 字段 | 管什么 | 取值 | 谁改 |
|---|---|---|---|
| `status` | **上下架**（货架上有没有它） | `1` 上架 / `0` 下架 | 管理员、审核动作 |
| `review_status` | **审核结论**（查过没有） | `pending` 待审 / `approved` 通过 / `rejected` 驳回 | 用户提交时、管理员审核时 |

> 生活化：`status` 是「灯亮不亮」，`review_status` 是「体检报告」。灯亮 + 报告通过 = 商城可见。

### 2.2 官方软件流程（提交即上架，不审核）

```
管理员在后台点「新增软件 / 上传安装包」
        │
        ▼
  POST /user/admin/software/create
  （服务端强制 source=official，review_status=approved）
        │
        ▼
   status=1  ──────────► 商城可见（带「官方」标记、置顶）
        │                      │
        │ 管理员点「下线」      │ 管理员点「删除」
        ▼                      ▼
   status=0（下架）      is_delete=1（软删除，不进商城）
        │
        └── 管理员点「上线」──► status=1 回到商城可见
```

### 2.3 用户上传流程（先审后上）

```
用户登录 → 商城页点「上传软件」
        │
        ▼
  POST /user/software/submit
  服务端写：source=user, review_status=pending, status=0
        │
        ▼
   ┌──────────────┐
   │ pending 待审核 │  ← 商城不可见；用户能在「我的提交」看到
   └──────┬───────┘
          │ 管理员在后台 review/list 看到
          ├──────────── approve（可带 note）────────► review_status=approved
          │                                              status=1
          │                                                │
          │                                                ▼
          │                                          商城可见（标「用户上传」）
          │
          └──────────── reject（note 必填）──────────► review_status=rejected
                                                         status=0
                                                           │
                                                           ▼
                                              用户看到驳回原因 → 修改后重新提交
                                              （重新提交生成新记录或重置为 pending，见 3.7）
```

> 注意：`approved` 之后管理员仍可以「下线」（`status=0`），此时 `review_status` 保持 `approved` 不变——「审过了」这件事不该因为一次下架就被抹掉。

### 2.4 状态与可见性对照表（前端验收就照这张表）

| `source` | `review_status` | `status` | 商城可见 | 说明 |
|---|---|---|---|---|
| official | approved | 1 | ✅ 可见（官方） | 管理员创建即此状态 |
| official | approved | 0 | ❌ 不可见 | 管理员手动下架 |
| user | pending | 0 | ❌ 不可见 | 刚提交 |
| user | approved | 1 | ✅ 可见（用户上传） | 审核通过 |
| user | rejected | 0 | ❌ 不可见 | 驳回，用户可见原因 |
| 任意 | 任意 | 1 且 `is_delete=1` | ❌ 不可见 | 软删除优先于一切 |

**公开列表的取数条件（前端按此验收）**：
```sql
WHERE is_delete = 0
  AND status = 1
  AND review_status = 'approved'
  [AND source = ?]          -- 传了 source 才过滤
```

## 三、接口清单

### 3.0 统一约定

| 项 | 约定 |
|---|---|
| 前缀 | `/apiAI`（前端 `.env` 里 `VITE_APP_REQUEST_HOST=https://www.rabbitj.top/apiAI`，下文路径都省略前缀） |
| 返回体 | `{ "code": 0, "data": {...}, "message": "ok" }`，`code` 为 `0` 才算成功 |
| 登录态 | 除公开发布列表外都要带 token |
| **token 怎么带** | 前端现有拦截器发的是 **`token: <token>` 请求头**（`src/request/index.ts`）。本文按你给的契约写 `Authorization: Bearer <token>`，**建议后端两种都认**：优先读 `Authorization: Bearer`，没有再读 `token`。这样现有后台页不用改就能用。 |
| 管理员校验 | `role = administrator`，否则 403 |
| 分页 | 请求 `page`（从 1 开始）、`page_num`（每页条数）；响应 `list`、`total`、`page` |
| 时间格式 | `YYYY-MM-DD HH:mm:ss`，后端本地时区 |
| 字符集 | UTF-8，JSON 用 `application/json; charset=UTF-8` |

**为什么建议两种 header 都认**：前端现在所有站内接口都用 `token` 头（这是历史包袱），如果新接口只认 `Authorization`，站长就得改一遍所有请求，容易漏。两个都认只是后端多几行判断，成本最低。

### 3.0.1 响应格式统一（现状与修正）· v3 新增

> **这是当前最大的联调障碍。** 3.0 写的统一约定是 `{code:0, data:{...}, message:"ok"}`，但线上接口**实际返回的不是这个格式**。两种格式并存会让前端时而正常、时而取不到数据，排错时非常费劲。本节把「现状」和「应该改成什么」一次说清。

#### ① 两种真实格式对照（2026-10-25 线上实测，非推测）

**A. 文档约定格式（3.0 写的，也是所有新接口应实现的）**

```json
{
  "code": 0,
  "data": { "list": [ ... ], "total": 4, "page": 1 },
  "message": "ok"
}
```

| 特征 | 值 |
|---|---|
| `code` 类型 | **数字** `0` |
| 数据结构 | 套在 **`data` 里** |
| 提示字段 | `message` |
| 分页位置 | `data.total` / `data.page` |

**B. 线上实测格式（`POST /user/software/list`，body `{"page":1,"page_num":20}`）**

```json
{
  "code": "0",
  "codeMsg": "成功",
  "list": [ ... ],
  "page": 1,
  "page_num": 20,
  "total": 4,
  "keyword": ""
}
```

| 特征 | 值 | 与约定的差异 |
|---|---|---|
| `code` 类型 | **字符串** `"0"` | ❌ 约定是数字 `0` |
| 数据结构 | **顶层 `list`**，无 `data` 包裹 | ❌ 严格按 `res.data.list` 取会拿到 `undefined` |
| 提示字段 | `codeMsg` | ❌ 约定是 `message`，两者并存容易混 |
| 分页位置 | **顶层** `total` / `page` / `page_num` | ❌ 位置不同 |

**同一份实测的逐字段核对结果**：

| 核对项 | 实测结果 |
|---|---|
| 顶层字段集合 | `code`(string)、`codeMsg`(string)、`list`(array)、`page`(number)、`page_num`(number)、`total`(number)、`keyword`(string) —— **没有 `data`、没有 `message`** |
| 单条记录的字段并集（13 个） | `id`、`category_id`、`category_name`、`name`、`summary`、`cover_url`、`version`、`links`、`sort`、`status`、`insert_time`、`update_time`、`is_delete` |
| **`source` / `platform` / `platforms`** | **一个都没有** —— 这是商城「官方软件」页签空白的直接原因（见 3.4） |
| `category/list` 是否同款问题 | **是，完全相同**：也是顶层 `list` + 字符串 `code` + `codeMsg`，**没有 `data`/`message`** |

#### ② 后果：说准，不夸大

站长最关心「会不会被误判成接口失败、页面变成空的」。实测结论要分开说：

| 担心的事 | 实际情况（依据前端源码 `src/request/index.ts`、`src/request/software.ts`） | 严重度 |
|---|---|---|
| 会不会让前端判断「接口失败」并进**本地模式**？ | **不会直接导致**。响应拦截器 `interceptorsResponse` 有一层「重包」：响应体不含 `code`+`data`+`message` 三件套时，会重包成 `{code: HTTP状态===200 ? 0 : status, data: 原body}`。所以这 4 条**能正常显示**——这正是「商城里有内容、官方页签却空着」的原因。 | 中 |
| 分页总数准不准？ | **不准**。前端读 `res.data.total`，而 `total` 在**顶层**，于是 `total` 退化成「当前页条数」。**数据一多，分页器就算错。** | **高** |
| 后端业务错误码还在不在？ | **被抹平**。重包后只要 HTTP 200，`code` 就恒为 `0`，后端真正的错误码（如 `4409`）**前端看不到**，无法按码分支处理。 | **高** |
| 后端的中文提示还能弹出来吗？ | **不能**。`codeMsg` 被埋在 `data` 里，前端读的是 `message`，用户只看得到「网络请求错误」这类兜底文案。 | 中 |
| 会不会白屏？ | 不会。`normalizeRecord()` 会补默认值，属于「降级显示」而非崩溃。 | 低 |

> 一句话：**不是「一调用就失败」，而是「看着能用，但分页错、错误提示丢、错误码失效」**——这类问题最难查，所以必须统一。

#### ③ 修正要求（后端按此实现，前端无需改调用方式）

| 项 | 要求 | 优先级 |
|---|---|---|
| `code` 类型 | **统一返回数字** `0`（成功）/ 非 0（失败） | **高** |
| 数据包裹 | 列表类统一放 **`data.list`**，分页放 **`data.total`** / `data.page` / `data.page_num` | **高** |
| 提示字段 | 统一用 **`message`**；`codeMsg` 可保留做兼容，但**必须同时给 `message`** | **高** |
| 顶层冗余 | 过渡期**允许**同时保留顶层 `list`/`total`（老前端在吃它），**但 `data` 里那份必须给** | 中 |
| 成功判定 | `code === 0` 才算成功（数字）；**不要再只返回 `"0"` 字符串** | **高** |

**修正后的标准成功响应（目标形态）**

```json
{
  "code": 0,
  "data": {
    "list": [ { "id": 4, "name": "余额兔", "source": "official" } ],
    "total": 4,
    "page": 1,
    "page_num": 20
  },
  "message": "ok"
}
```

**过渡期兼容策略（照顾线上老前端，避免一刀切出事）**

| 阶段 | 后端返回 | 前端行为 |
|---|---|---|
| 阶段 1（现在） | 顶层 `list` + 字符串 `code` + `codeMsg` | 能显示，但分页数不准、错误提示丢（见 ②） |
| **阶段 2（建议尽快）** | **同时**返回 `data.list/total/page` **和**顶层 `list/total`；`code` 给数字 `0`，`codeMsg` 与 `message` 都给 | ✅ 全部正常，老调用方也不受影响 |
| 阶段 3（稳定后） | 只留 `data.*` + `message`，删掉顶层冗余 | ✅ 正常 |

> **为什么允许分三步**：站长的站正在跑，用户正在下载软件。**阶段 2「两份都给」是零风险中间态**，新旧前端都能读；观察几天没问题再进阶段 3。

#### ④ 前端兼容现状（已实现，后端改完不用通知前端改代码）

| 前端行为 | 源码位置 | 说明 |
|---|---|---|
| `code` 数字/字符串都认 | `isOk()`：数字比 `=== 0`；否则再看 `res.data.code === 0` 或 `'0'` | 后端给 `"0"` 或 `0` 都不会挂 |
| `list` 多位置兜底 | `payload.list \|\| payload.data \|\| []` | 顶层 `list`、`data.list`、`data.data` 都能读 |
| `total` 有兜底 | `Number(payload.total \|\| normalized.length)` | 后端不给 `total` 时用当前页条数顶上（**所以后端必须给准 `total`**） |
| 响应重包 | `interceptorsResponse`：不含三件套时重包 | 保证老格式不崩，但**会抹平错误码**（见 ②） |

### 3.1 `POST /user/admin/software/upload`（管理员上传文件）

- **鉴权**：管理员（`role=administrator`）
- **Content-Type**：`multipart/form-data`
- **用途**：管理员在后台「软件下载」页上传安装包或封面，拿到 `url` 后再调 `create`。

**请求字段**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `file` | file | 是 | 单文件；安装包 ≤ **200MB**；封面 ≤ 5MB |
| `kind` | string | 是 | `package`（安装包） 或 `cover`（封面图） |

**成功响应**

```json
{
  "code": 0,
  "data": {
    "url": "https://cdn.example.com/software/2026/10/25/a1b2c3d4/MyApp-1.0.0-win-x64.exe",
    "file_name": "MyApp-1.0.0-win-x64.exe",
    "file_size": 48234496
  },
  "message": "ok"
}
```

| 返回字段 | 类型 | 说明 |
|---|---|---|
| `url` | string | 直链（建议对象存储 + 签名，见第 4 节） |
| `file_name` | string | 原始文件名（已清洗，见 4.4） |
| `file_size` | number | 字节数。**注意**：老字段 `file_size` 在旧数据里是 `"12.4 MB"` 这种字符串，新接口一律返回字节数字，前端负责格式化显示 |

**失败响应**

| HTTP | code | 场景 | message 示例 |
|---|---|---|---|
| 401 | 4001 | 未登录/token 失效 | 请先登录 |
| 403 | 4003 | 不是管理员 | 仅管理员可上传 |
| 413 | 4413 | 文件超过 200MB | 安装包不能超过 200MB |
| 415 | 4415 | 类型不在白名单 | 只支持 exe/dmg/zip/AppImage/deb |
| 422 | 4422 | 缺 `file` 或 `kind` 非法 | 请选择要上传的文件 |

**幂等与限流**：非幂等（每次上传都产生新文件）。建议 **管理员 30 次/小时**，超限 `429 / 4429`。

### 3.2 `POST /user/admin/software/create`（管理员创建/直传上架）

- **鉴权**：管理员
- **说明**：**复用现有接口**（前端 `createAdminSoftware` 已存在），只在原有字段上做**增量扩展**。管理员创建 = 官方软件 = 直接上架。
- **v2 变更**：新增 **`platforms` 数组**（多平台复选），`platform`（单数）**降为兼容期可选**。两者的优先级见下方「优先级规则」。

**请求字段**

| 字段 | 类型 | 必填 | 约束 | 新/旧 |
|---|---|---|---|---|
| `category_id` | number | 是 | 必须是存在的分类 | 旧 |
| `name` | string | 是 | 1–200 字 | 旧 |
| `summary` | string | 否 | ≤ 5000 字 | 旧 |
| `cover_url` | string | 否 | 图片地址，或 base64 dataURL（前端已压缩到 ≤180KB） | 旧 |
| `links` | array | 否 | `[{label,url,code}]`，兼容原有外链/网盘 | 旧 |
| `sort` | number | 否 | 0–999999，越大越靠前 | 旧 |
| `source` | string | 否 | 服务端**强制** `official`，前端传什么都忽略 | v1 |
| **`platforms`** | **array** | **否**（但与 `platform` 二选一，至少给一个） | **1–3 个元素**；同一数组内 `platform` **不可重复**；元素结构见下表 | **v2 新增** |
| `platforms[].platform` | string | 是（元素内） | `windows` \| `macos` \| `linux` | v2 新增 |
| `platforms[].file_url` | string | 是（元素内） | 安装包直链或网盘链接；**三个平台可填同一条** | v2 新增 |
| `platforms[].file_size` | number | 否 | 字节。**包体积总大小**概念只在单平台时准确，多平台未知可省略或传 `0` | v2 新增 |
| `platforms[].version` | string | 否 | **每个平台可各自一个版本号**，不传则回退到顶层 `version` | v2 新增 |
| `platform` | string | 否 | `windows` \| `macos` \| `linux`；**兼容期保留**，等价于 `platforms` 只有一个元素 | v1（v2 降级） |
| `version` | string | 否 | 如 `1.0.0`；作为**默认版本号**，被 `platforms[].version` 覆盖 | 旧（语义扩展） |
| `file_url` | string | 否 | 兼容期保留，等价于 `platforms[0].file_url` | v1（v2 降级） |
| `file_size` | number | 否 | 字节，兼容期保留 | v1（v2 降级） |
| `changelog` | string | 否 | ≤ 2000 字 | v1 |
| `status` | number | 否 | 默认 `1`；管理员创建即上架 | 旧 |

**优先级规则（v2 新增，前端与后端都必须照此实现）**

| 前端实际传了什么 | 后端怎么处理 | 结果 |
|---|---|---|
| 只传 `platforms`（推荐写法） | 以 `platforms` 为准，每个元素建一条 release | 多平台，按数组个数 |
| `platforms` + `platform` 都传了 | **以 `platforms` 为准，`platform` 直接忽略**（不报错、不合并） | 多平台，按数组个数 |
| 只传 `platform`（老前端 / 老调用方） | 服务端内部按 `platforms = [{ platform, file_url, file_size }]` **单元素数组**处理 | 单平台，行为与 v1 完全一致 |
| 两个都没传 | `422 / 4422`，`message`：「请至少选择一个平台」 | 失败 |
| `platforms` 传了空数组 `[]` | `422 / 4422` | 失败 |
| `platforms` 里同一 `platform` 出现两次 | `422 / 4422`（或后端取第一条并忽略重复，**建议直接 422**，便于前端早发现） | 失败 |

> 为什么「以 `platforms` 为准」而不是反过来：`platforms` 是信息更全的那一个，能表达「三个平台一个链接」；单数 `platform` 表达不了。**丢弃信息少的一方，不会丢用户填的内容。**
> 为什么还要保留 `platform`：线上老前端、老调用方还在用单数，直接删字段会让它们创建失败。**保留 = 平滑过渡**，等前端全部切到 `platforms` 后再择期废弃（见待确认清单第 19 条）。

**请求示例 A：三个平台共用同一个链接（站长最关心的场景）**

```json
{
  "category_id": 3,
  "name": "记账小工具",
  "summary": "记录每天花了多少钱，Windows/macOS/Linux 都能用",
  "source": "official",
  "version": "1.0.0",
  "platforms": [
    { "platform": "windows", "file_url": "https://github.com/me/tool/releases/tag/v1.0.0", "file_size": 0 },
```

**成功响应**

```json
  "code": 0,
```

| HTTP | code | 场景 | message 示例 |

**幂等**：非幂等。**建议限流** 20 次/小时/管理员（多平台一次提交算 **1 次**，不按平台个数叠加）。

### 3.3 `POST /user/admin/software/update`（管理员编辑/上下架/删除）

- **鉴权**：管理员
- **说明**：复用现有接口，支持同样扩展字段 + `is_delete`。**只传要改的字段**（局部更新）。

**请求字段**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | number | 是 | 软件 ID |
| `category_id` / `name` / `summary` / `cover_url` / `links` / `sort` | 同 3.2 | 否 | 局部更新 |
| `version` / `changelog` | 同 3.2 | 否 | 局部更新 |
| **`platforms`** | array | 否 | **v2 新增**。语义见下方「`platforms` 在 update 里的两种语义」 |
| `platform` / `file_url` / `file_size` | 同 3.2 | 否 | 兼容期保留，仅影响**单个**平台 |
| `status` | number | 否 | `0` 下架 / `1` 上架 |
| `is_delete` | boolean | 否 | `true` = 软删除（不进任何列表） |

> `source` 不允许通过 update 修改（官方/用户身份不可串改），传了也忽略。

**`platforms` 在 update 里的两种语义（v2 新增，必须由后端确认采用哪一种）**

| 语义 | 行为 | 适用场景 | 风险 |
|---|---|---|---|
| **增量更新（推荐）** | 传了哪几个平台就只改那几个平台，**没传的平台保持原样**；某平台传 `status: 0` 即下架该平台 | 只给 macOS 补一个包（3.12 第 3 问） | 无 |
| 整体替换 | 以数组为全集，**不在数组里的平台视为删除/下架** | 一次改全部 | 前端漏传一个平台，就会误下架该平台；**不推荐** |

> **建议采用「增量更新」**，并在本文钉死：`platforms` 只增改、不隐含删除；要下架某平台，必须显式传该平台条目并带 `status: 0`。这样「给某平台补包」不会误伤其它平台。
> **待后端确认**：现有 update 接口若为整体覆盖实现，需改造为增量；改造期间可先只支持 `platform`（单数）局部更新，前端降级。

**成功响应**：`{"code":0,"data":{"id":128},"message":"ok"}`

**失败响应**：401 / 403 / 404（`4404` 软件不存在）/ 422（含 `platforms` 结构非法）/ 409（该平台已有在架版本）。

**幂等**：**幂等**（同样参数重复调用结果一致）——这是前端「上线/下线」按钮会重复点的原因，后端要保证幂等。**多平台同理**：重复传同一份 `platforms` 不应产生重复 release 行。

|---|---|---|
| 有 `platforms[]`（≥1 条） | 按数组渲染多平台图标，每个平台一个下载按钮 | 三个平台图标 + 三个下载按钮（链接相同也照常显示三个入口） |
| **没有 `platforms` 字段**（老后端） | **降级**：若 `platform` + `file_url` 有值，则用它们合成一个单元素数组 `[{ platform, version, file_url, file_size, download_count }]` | 只显示一个平台图标 + 一个下载按钮，**功能不坏** |
| `platforms: []` 且 `platform` 为空 | **降级**：卡片显示「暂未提供下载」，不显示下载按钮，**不报错、不白屏** | 卡片可见但不可下载，提示「作者还没上传安装包」 |
| `platforms` 存在但某平台 `file_url` 为空 | 该平台图标置灰不可点，其余平台正常 | 灰掉的那个平台显示「暂无此平台安装包」 |
| `platforms` 不是数组（类型错） | 按「没有 `platforms` 字段」处理，走上面第 2 条降级 | 与老后端一致 |

> 降级原则一句话：**有数组就用数组，没数组就退回单数，两者都没有就显示「暂未提供下载」——任何情况都不许白屏或报错。**

**失败响应**：401（如果后端要求登录，前端会提示登录）；500。

**排序建议**：`source='official'` 优先（官方置顶）→ `sort DESC` → `update_time DESC`。

#### 3.4 附：`source` 取值规则与存量回填（v3 新增）

**取值规则（只有两个值，没有第三种）**

| `source` 值 | 什么情况用它 | 谁写 | 审核 | 商城显示 |
|---|---|---|---|---|
| `official` | 管理员在后台「管理员直传」上传的、我们自己有权限维护的软件 | **服务端强制**（`create`/`update` 不许前端指定） | 不需要（直接 `approved`） | 「官方」标记 + 置顶 |
| `user` | 注册用户通过「上传软件」提交的 | **服务端强制**（`submit` 一律写 `user`） | 必须审核通过才可见 | 「用户上传」标记 |

**硬性要求（后端照做，否则商城页签又会错）**：

1. **必返**：`list`（3.4）、`detail`（3.5）、`review/list`（3.9）三处的每一条记录都要带 `source`。
2. **不许 null / 空串**：`source` 为空时前端无法判断，等同于缺字段。
3. **不许从请求里采信**：`create` 传 `source=user` 也必须落 `official`；`submit` 传 `official` 也必须落 `user`（防冒充）。
4. **字段名不要改**：就叫 `source`，不要写成 `source_type`、`origin`、`is_official`。

**存量数据回填 SQL（旧记录如何判定为官方）**

> 判定依据：**存量记录都是站长自己手录的**（此前只有后台「软件下载」页能增删改，没有对外开放的用户提交入口），因此全部按 `official` 回填是安全的。

```sql
-- ⚠️ 执行前先备份（至少导出软件表）
-- mysqldump -u root -p <dbname> software > backup_software_before_source_20261025.sql

-- 1) 先查：看现在缺 source 的有几条、分别是谁（只读，先看清楚）
SELECT id, name, category_id, status, is_delete
FROM software
WHERE source IS NULL OR source = '';

-- 2) 回填：存量一律视为官方
UPDATE software
SET source = 'official'
WHERE source IS NULL OR source = '';

-- 3) 核对：回填后不应再有空值（应为 0 行）
SELECT COUNT(*) AS still_missing FROM software
WHERE source IS NULL OR source = '';

-- 4) 核对分布：应全部落在 official
SELECT source, COUNT(*) AS cnt FROM software GROUP BY source;
```

> **注意**：如果后端采用「`source` 列 `NOT NULL DEFAULT 'official'`」（5.1 的 DDL 就是这么写的），那么在加列的那一刻，存量行**已经自动是 `official`**，第 2 步 UPDATE 会影响 0 行——**这是正常的，不是出错**，跑一遍只为兜住「列已存在但值为空」的情况。

### 3.4.1 `category_id` 筛选逐条验证（v3 新增）

> 站长反馈「`category_id` 筛选似乎未生效」。**实测结论：筛选是生效的**，问题在别处。本节把「入参支持到哪一步」和「实测数据」逐条列清。

#### ① 结论先说

| 问题 | 结论 | 依据 |
|---|---|---|
| `list` 的 `category_id` 入参**生效吗**？ | ✅ **生效** | 实测 `category_id=1` → 返回 3 条（id 1/2/3，均 `category_id=1`）；`category_id=3` → 返回 1 条（id=4 余额兔）。`total` 同步变化（3 / 1） |
| 那「筛选未生效」是怎么回事？ | ❌ **是「写入时分类存错」，不是「查询筛不动」** | 站长上传时选的是 AI(Agent)，但记录落在「效率软件」（`category_id=3`）。说明 **`create` 没有按前端传的 `category_id` 落库**，或前端下拉当时只有 1 个分类、实际下发的是别的值。**这一点仍需后端/实测 `create` 确认** |
| `category_id` 传 `null` 会怎样？ | ✅ 等于不筛选（返回全部） | 前端 `getSoftwareList` 就是这么传的：`category_id: params.category_id \|\| null` |
| 分类 id 与 `category/list` 一致吗？ | ✅ 一致 | 实测 `category/list` 返回 `id=3 效率软件`、`id=1 AI(Agent)软件`，与 `list` 里记录的 `category_id` 对得上 |
| `source` 参数生效吗？ | ❌ **不生效（实测）** | 传 `source=official` 和 `source=user`，返回的都是**同样的 4 条**（`total` 都是 4）。因为表里根本没有 `source` 列/字段（见 3.0.1）。**修完 `source` 字段后必须同时把筛选接上** |

#### ③ 要求后端确认并照此实现

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **`category_id` 筛选按「等于」实现**（`WHERE category_id = ?`），不是 `LIKE`、不是忽略 | 接入指南要用它精确取「AI(Agent)」这一个分类 |
| 2 | **`create` / `update` 必须真正保存前端传的 `category_id`** | 站长这次就是选了 AI(Agent) 却落到效率软件。**这是「存」的问题，不是「筛」的问题** |
| 3 | **`category_id` 不合法时返回 422**，不要静默改成默认分类 | 静默改值会让数据无痕跑偏，站长根本查不出来 |
| 4 | `/user/software/category/list` 返回的 `id` 与 `create` 传的 `category_id` **必须是同一套 id** | 两套 id 体系会让筛选永远筛不到东西 |
| 5 | 修完 `source` 字段后，**`source` 筛选参数要一起接上** | 否则商城「官方/用户上传」页签只能靠前端自己 filter，分页会错 |

**校验 SQL（后端自查用）**

```sql
SELECT id, name, category_id, source, status, insert_time
FROM software
ORDER BY id;

-- ② 传 category_id=3 时，接口是否只返回 category_id=3 的记录？
```

#### ⑤ 商城新增「分类筛选」栏（2026-10-25 站长新增需求，前端已实现）

**站长原话**：「只要我们在后台增加了一个分类，那么在这个软件商城中也能够看到相应的分类……点击相应的类目就能够筛选出来。」

**前端实现方式**：商城在原有「全部 / 官方软件 / 用户上传 / 我的提交」这一排**下面再加一排分类按钮**，按钮由 `category/list` 返回的数据生成——**后台加一个分类，商城就自动多一个按钮，前端不写死任何分类名或 id**。

**这给后端带来 4 条硬性要求**（缺任何一条，商城的分类栏就会出错）：

| # | 要求 | 不做会怎样 |
|---|---|---|
| 1 | `category/list` 必须只返回**有效**分类：`status=1` 且 `is_delete=false`（前端也会再过滤一次，但后端应先保证） | 用户会看到已停用/已删除的分类，点进去永远是空的 |
| 2 | `list` 的 `category_id` 入参**必须真正过滤**（当前实测生效，请保持） | 点了分类但列表不变，用户以为坏了 |
| 3 | `category_id = null` / 不传时**返回全部**（不要当成「没有分类」） | 「全部分类」按钮会得到空列表 |
| 4 | 每条 `list` 记录**必须返回 `category_id`**（数字），当前已返回，请保持 | 前端无法把记录归入分类；漏了该字段的记录只会在「全部分类」下显示，具体分类下看不到 |

**两层筛选的组合语义**（后端只需支持单条件 `category_id`，组合在前端做）：

| 用户操作 | 实际行为 |
|---|---|
| 官方软件 + 效率软件 | 前端取官方集合，再本地筛该分类 |
| 官方软件 + 全部分类 | 不带 `category_id` |
| 我的提交 | **不显示分类栏**（个人投稿记录按分类筛无意义） |

> 说明：因为组合在前端完成，后端**不需要**支持 `source` 与 `category_id` 同时传的复杂查询。若服务端愿意一并支持，前端也兼容——只要单条件语义正确即可。

### 3.4.2 ⚠️ 分页上限 `page_num ≤ 50`（v3 补，这是「本地模式」的真凶）

> **2026-10-25 实测确认**（本次 bug 排查中最容易误判的一条）：

| 请求 | 结果 |
|---|---|
| `{"page":1,"page_num":50}` | ✅ `code:"0"`，正常返回 |
| `{"page":1,"page_num":51}` | ❌ **HTTP 422** |
| `{"page":1,"page_num":100}` | ❌ **HTTP 422** |

422 的原文：

```json
{"detail":[{"type":"less_than_equal","loc":["body","page_num"],
  "msg":"Input should be less than or equal to 50","input":100,"ctx":{"le":50},
  "url":"https://errors.pydantic.dev/2.5/v/less_than_equal"}]}
```

**为什么这条很关键**：前端商城页原来请求 `page_num: 100`（想一次取全量），被后端 422 拒绝；前端把这次调用判为失败，于是**整页显示「本地模式」、列表一片空白**——站长看到的现象是「商城打不开」，而真实原因只是分页参数超限。排查时很容易误以为是登录态、跨域或响应格式问题。

**契约要求**

| 项 | 要求 |
|---|---|
| `page_num` 上限 | **50**（Pydantic `le=50`）。请保持不变并在文档中固化，不要随意调低 |
| 超限响应 | 建议返回**可读的中文提示**，而不是 Pydantic 原始 `detail` 数组；至少保证前端能识别为「参数错误」而非「系统故障」 |
| 前端已做的防护 | `getMarketList()` 内部统一 `Math.min(page_num, 50)`；商城页也改成传 50。**任何调用方写多大都不会再把商城搞空** |
| 若要全量数据 | 用翻页循环（`page=1..n`）或另开一个不分页的管理端接口，**不要靠调大 `page_num`** |

> 顺带记录一条同类问题：`GET /user/software/my-submissions` 在未登录时返回 `code 3004`，测试中亦见过 500。它不是「本地模式」的主因（主因就是上面的 422），但**上传者的「我的提交」页签依赖它，需要后端确认实现状态**。

### 3.5 `GET /user/software/detail?id=`（详情页，可选）

- **鉴权**：不需要
- **说明**：未实现时前端从 list 里按 id 找，不报错。**可以不实现**。

**成功响应**：返回单个软件对象，结构同 3.4 的列表项，另可带 `changelog`。

**v3 强制（必返字段）**：本节对象**必须包含 `source`**（`official` / `user`），规则同 3.4 附。**只在这一处返回 `source` 是不够的**——商城页签是对 `list` 的结果做过滤，`detail` 缺 `source` 只会让详情页标签显示错。

| 返回字段 | 必返 | 说明 |
|---|---|---|
| **`source`** | **✅ 必须** | `official` / `user`；不许 null/空串。取值规则见 3.4 附 |
| `category_id` | **✅ 必须** | 与 `category/list` 同一套 id（见 3.13） |
| `platforms[]` | ✅ 必须 | 与 3.4 完全同构；无数据返回 `[]` |

> **实测提醒（2026-10-25）**：线上 `GET /user/software/detail?id=4` 当前返回 `{"code":"3004","codeMsg":"用户状态已过期"}`，即**要求登录**，与本节的「不需要鉴权」不一致。前端已有降级（从 `list` 按 id 找），**不阻塞**；但请后端确认按哪种实现（待确认清单第 3 条）。

**v2 明确**：详情页的 `platforms[]` **与列表完全同构**（`platform/version/file_url/file_size/download_count`），前端详情页与卡片共用同一套渲染逻辑，不再另定一套字段。**降级规则同 3.4**（没有 `platforms` 就退回单数 `platform`）。

> 详情页需要展示**历史版本**时，才额外加 `releases[]`（含已下架版本 + `insert_time`）；**默认不返回历史版本**，避免用户下到旧包。这条属可选项，前端暂不依赖。

**失败响应**：404 `4404` 软件不存在 / 已下架。

### 3.6 `POST /user/software/submit`（用户提交软件）

- **鉴权**：登录用户
- **关键规则（后端必须兜底，不信前端）**：
  1. 服务端强制写 `source='user'`、`review_status='pending'`、`status=0`；前端传了 `official` 也没用。
  2. 同一用户对同一 `name` + 同一 `platform` 重复提交，视为**发新版本**（挂到已有软件下），但仍走 `pending`。
  3. 名字不要和官方软件重名（建议 `409`，防止用户冒充官方）。

**请求字段**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `name` | string | 是 | 1–200 字 |
| `summary` | string | 是 | 1–5000 字 |
| `category_id` | number | 是 | 必须存在 |
| `version` | string | 是 | 1–50 字 |
| `platforms` | array | 是 | **1–3 条**：`[{ platform, file_url, file_size }]`；**同一数组内 platform 不可重复**；**三条 `file_url` 可完全相同** |
| `platforms[].platform` | string | 是 | `windows`\|`macos`\|`linux` |
| `platforms[].file_url` | string | 是 | 直链或网盘链接 |
| `platforms[].file_size` | number | 否 | 字节，未知可省略 |
| `platforms[].version` | string | 否 | **v2 新增（与 3.2 对齐）**：该平台单独版本号，不传回退顶层 `version` |
| `changelog` | string | 否 | ≤ 2000 字 |
| `repo_url` | string | 否 | 代码仓库地址 |

> **v2 对齐说明**：`submit` 本来就用 `platforms` 数组，v2 **不改变它的形状**，只补两条与 `create` 一致的规则：①（可选）支持 `platforms[].version` 各平台版本不同；② 多个平台填**同一条链接是合法的**（站长场景：一个网盘文件夹三平台都能下）。审核粒度见 3.9.1（整条审）。

**请求示例**

```json
{
  "name": "我自己写的记账小工具",
  "summary": "记录每天花了多少钱，界面很简单",
  "category_id": 3,
  "version": "0.1.0",
  "platforms": [
    { "platform": "windows", "file_url": "https://pan.example.com/s/abc123", "file_size": 0 }
  ],
  "changelog": "第一个版本",
  "repo_url": "https://github.com/me/tool"
}
```

**成功响应**

```json
{ "code": 0, "data": { "id": 201, "review_status": "pending" }, "message": "ok" }
```

> 列表类接口（3.4 / 3.7 / 3.9）的 `list` 请放在 `data.list` 下。前端为了容错，会退一步读 `data.data`，但**这是兜底不是契约**，请不要依赖：统一按 `data.list` 返回。

**失败响应**

| HTTP | code | 场景 |
|---|---|---|
| 401 | 4001 | 未登录 |
| 409 | 4409 | 与官方软件重名 |
| 422 | 4422 | 必填缺失 / `platforms` 为空 / platform 非法 |
| 429 | 4429 | 提交太频繁 |

**逻辑与限流**：非幂等（重复提交会产生新记录或新版本）；建议 **5 次/天/用户**、单用户 `pending` 记录 ≤ 10 条。

### 3.9 `GET /user/admin/software/review/list`（待审队列）

- **鉴权**：管理员

**请求参数**

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `status` | string | `pending` | `pending`\|`approved`\|`rejected` |
| `page` | number | 1 | |
| `page_num` | number | 10 | ≤ 50 |

**成功响应**：`data.list` 结构同 3.7，**额外带** `author_user_id`、`author_name`、`category_name`、`reviewer_name`（可空）。

**v3 强制（必返字段表）**

| 返回字段 | 必返 | 说明 |
|---|---|---|
| **`source`** | **✅ 必须** | 队列里恒为 `user`（官方不进队列），但**字段必须返回**，不要因为「反正都是 user」就省略——前端按 `source` 统一渲染标签，缺字段会显示成「用户上传」之外的空标签 |
| `review_status` | ✅ 必须 | `pending` / `approved` / `rejected` |
| `category_id` | ✅ 必须 | 与 `category/list` 同一套 id；**用于后台核对「这条投稿落在哪个分类」** |
| `category_name` | ✅ 必须 | 与 `category_id` 对应 |
| `platforms[]` | ✅ 必须 | 与 3.4 同构；无数据返回 `[]` |
| `author_user_id` / `author_name` | ✅ 必须 | 审核人要看是谁提交的 |
| `reviewer_name` | 可为 `null` | 还没审时为 `null` |

> **为什么 3.9 也要 `source`**：站长的 bug 是「后台直传的软件跑进接入指南」。后台审核页与队列若缺 `source`，管理员也无法一眼分辨「这条是官方还是用户提交」。**三个接口（3.4 / 3.5 / 3.9）必须一起返 `source`，缺一处就会在一处出错。**

**v2 明确（多平台）**：

1. 队列里**一条投稿 = 一行**，该投稿包含的所有平台放在 `platforms[]` 数组里（**与 3.4 同构**）。管理员在后台看到的是「一个软件 + 它包含的 1–3 个平台包」，而不是三条待审记录。
2. `platforms[]` 每个元素额外建议带 **`review_status`**（v2 新增，可选），用于未来按平台审核时展示每个平台各自的审核状态；**整条审核时该值与软件级 `review_status` 一致**，前端可忽略。
3. 建议顺带返回 `platform_count`（该投稿的平台个数），方便后台列表显示「3 个平台」角标。**可选字段，前端不硬依赖。**

**示例（片段）**

```json
{
  "id": 201,
  "name": "我自己写的记账小工具",
  "source": "user",
  "review_status": "pending",
  "status": 0,
  "author_user_id": 10086,
  "author_name": "小明",
  "category_name": "桌面工具",
  "reviewer_name": null,
  "platform_count": 3,
  "platforms": [
    { "platform": "windows", "version": "0.1.0", "file_url": "https://pan.example.com/s/abc123", "file_size": 0, "review_status": "pending" },
    { "platform": "macos",   "version": "0.1.0", "file_url": "https://pan.example.com/s/abc123", "file_size": 0, "review_status": "pending" },
    { "platform": "linux",   "version": "0.1.0", "file_url": "https://pan.example.com/s/abc123", "file_size": 0, "review_status": "pending" }
  ]
}
```

**说明**：只返回 `source='user'` 的记录（官方软件不需要审，不进队列）。

**失败响应**：401 / 403。

### 3.9.1 审核粒度：整条审 vs 按平台审（v2 新增，需拍板）

**结论：推荐「整条审」。**

| 方案 | 怎么做 | 优点 | 代价 | 建议 |
|---|---|---|---|---|
| **① 整条审（推荐）** | 一次 `approve` / `reject` 作用于**整个投稿**（主表 `software.review_status` + 该投稿所有 release 一起改） | 现有 3.10 接口**完全不用改**；管理员只做一次决定；驳回原因只有一份，用户看得懂 | 不能「Windows 通过、macOS 驳回」；一个平台的包坏了会整条打回 | ✅ **v2 采用这个** |
| ② 按平台审 | `review` 接口增加 `platform` 参数，逐平台 `approve`/`reject`；主表 `review_status` 由聚合规则推导 | 精细，一个平台坏了不影响其它平台上线 | 接口要加参数；审核队列一个投稿要点 3 次；驳回原因要按平台存（`reviewer_note` 需变成「按平台一组」）；前端审核页要重做 UI；状态聚合规则多（全通过=approved？部分通过=partial？） | ⏳ 后续有明确需求再做 |

**如果将来要改成「按平台审」，表结构这样变（先写在这里，避免以后推倒重来）**：

| 改动 | 具体做法 |
|---|---|
| `software_release` 已具备条件 | 该表**本来就有** `review_status`、`reviewed_at` 字段（见 5.2），按平台审时直接用起来，**不需要加列** |
| 驳回原因要分平台 | `software_release` 增加 `reviewer_note VARCHAR(500) NULL`（与主表同名同义，但存该平台的驳回原因） |
| 增加审核人 | `software_release` 增加 `reviewer_user_id BIGINT UNSIGNED NULL` |
| 主表 `review_status` 变「聚合值」 | 建议规则：全部 approved → `approved`；全部 rejected → `rejected`；其余（含部分通过）→ `pending` + 另加 `partial` 枚举值（需 `ALTER` 枚举）。**这条规则必须提前定死，否则前端状态显示会乱** |
| 队列查询 | `review/list` 的 `?status=pending` 改为查「任一 release 为 pending」的软件，且返回每个 release 的 `review_status`（3.9 已预留该字段） |
| 审核接口 | `review` 增加可选 `platform`：传了就只审该平台，不传 = 整条审（**向后兼容**，前端现有调用不用改） |

> 一句话：**现在按整条审最省事，且 5.2 的 `software_release` 已经把按平台审需要的字段留好了**——先用整条审上线，将来要精细再开 `platform` 参数，不用改表。

### 3.10 `POST /user/admin/software/review`（审核动作）

- **鉴权**：管理员

**请求字段**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `id` | number | 是 | 软件 ID |
| `action` | string | 是 | `approve` \| `reject` |
| `note` | string | reject 时必填 | 1–500 字；**传空字符串 `""` 视为未填**——前端 `reviewSoftware` 在 approve 时会显式传 `note: ""`，后端不能因此报 422 |

**请求示例**

```json
{ "id": 201, "action": "reject", "note": "安装包链接失效了，请换一个能下载的地址" }
```

**状态变化**

| action | `review_status` | `status` | 额外写入 |
|---|---|---|---|
| `approve` | `approved` | `1` | `reviewer_user_id`、`reviewed_at` |
| `reject` | `rejected` | `0` | `reviewer_user_id`、`reviewed_at`、`reviewer_note` |

**成功响应**：`{"code":0,"data":{"id":201,"review_status":"approved"},"message":"ok"}`

**v2 多平台语义（与 3.9.1 的「整条审」配套）**

| 项 | 规则 |
|---|---|
| 作用范围 | **一次动作作用于该投稿的全部平台**：主表 `review_status`/`status` 改，同时把该投稿所有 `software_release` 行的 `review_status`/`status` 一起改成一致值 |
| `approve` | 主表 `status=1`；**该投稿下每个平台各有一条在架 release**（三平台同链接 → 三条 release 都 `status=1`） |
| `reject` | 主表 `status=0`；该投稿所有 release `status=0`；`reviewer_note` **只写一份**（主表），驳回原因是给整条投稿的，**不按平台各写一份** |
| 是否支持按平台审 | **v2 不支持**（`platform` 参数暂不接受；传了建议忽略或 422，**待后端确认取哪种**）。将来支持时按 3.9.1 表格扩展，且不传 `platform` 时行为与本版完全一致（向后兼容） |
| 唯一约束注意 | `approve` 时若某平台已有在架版本，**先自动把旧 release 置 `status=0`**，再上架新的，避免触发 5.2 的唯一键 `uk_sw_active_platform` 报错（同 8.2 自测清单那条） |
| 限流 | 不限流（管理员操作），但**同一记录重复审核返回 409**，见下表 |

**失败响应**

| HTTP | code | 场景 |
|---|---|---|
| 401 | 4001 | 未登录 |
| 403 | 4003 | 非管理员 |
| 404 | 4404 | 记录不存在 |
| 409 | 4409 | 该记录不是 `pending`（已被处理，防重复审批） |
| 422 | 4422 | `reject` 未填 `note` / `note` 超 500 字 |

**幂等**：**状态机保护**——只有 `pending` 能被审核；重复提交返回 `409`（或直接返回成功但不再改状态，二选一，**建议 409**，前端好提示「已处理」）。

### 3.11 错误码总表

| HTTP | code | 含义 | 前端展示建议 |
|---|---|---|---|
| 400 | 4400 | 参数格式错（JSON 解析失败等） | 请求有误，请刷新重试 |
| 401 | 4001 | 未登录 / token 失效 | 自动跳登录（前端已有逻辑） |
| 403 | 4003 | 非管理员 | 仅管理员可操作 |
| 404 | 4404 | 记录不存在 | 这条记录已不存在 |
| 409 | 4409 | 冲突（重名 / 已审核 / 同平台已有在架版本） | 直接展示 message |
| 413 | 4413 | 文件过大 | 安装包不能超过 200MB |
| 415 | 4415 | 文件类型不支持 | 只支持 exe/dmg/zip/AppImage/deb |
| 422 | 4422 | 字段校验失败 | 直接展示 message（要写清哪个字段） |
| 429 | 4429 | 触发限流 | 操作太频繁，请稍后再试 |
| 500 | 4500 | 服务端异常 | 服务暂时不可用，请稍后再试 |
| 410 | 4410 | 旧接口已下线（仅 `/open-source/*`） | 该功能已升级，请刷新页面 |

> 约定：**所有失败都要给 `message`**，而且要能直接给用户看（中文、说清怎么办）。前端会把 `message` 弹出来。

### 3.12 多平台常见 FAQ（v2 新增）

> 这一节是给站长看的：把「一个链接三个平台」这类常见疑问一次说清。每条都是**结论 + 为什么**，后端按结论实现即可。

**第 1 问：同一个链接三个平台都能下，后端怎么存？**

**答：存三条 `software_release`，`file_url` 三条一模一样，不合并。**

| 项 | 做法 |
|---|---|
| 存法 | `software` 1 行（软件本体）+ `software_release` **3 行**（windows / macos / linux 各 1 行），三行 `file_url` 相同 |
| 为什么不合并成一行 | **下载统计要分平台**：合并了就无法知道「Windows 下了 700 次、macOS 下了 300 次」；也没法只给某一个平台换链接 |
| 会不会浪费空间 | 不会。`software_release` 一行只有几百字节，一个链接存三遍可以忽略 |
| 前端怎么显示 | 三个平台图标、三个下载按钮，点哪个都跳同一个链接——**用户视角正常，后台视角可统计** |
| 唯一约束 | 三行 `platform` 不同，`(software_id, platform)` 天然不冲突，唯一键不会报错 |

> 生活化：就像一件商品有「红/蓝/黑」三个颜色，链接（购买页）可以是同一个，但销量要按颜色分开记。

**第 2 问：我只有 Windows 包怎么办？**

**答：`platforms` 只传一个元素就行，其它平台在商城不显示下载按钮。**

```json
"platforms": [{ "platform": "windows", "file_url": "https://...", "file_size": 48234496 }]
```

| 项 | 行为 |
|---|---|
| 商城卡片 | 只显示 1 个 Windows 图标 + 1 个下载按钮 |
| 其它平台 | **完全不出现**（不显示灰掉的 macOS/Linux 按钮，避免用户误以为漏发了包） |
| 后端 | 只建 1 条 release；`software.platform` 可冗余存 `windows` 便于老接口 |
| 以后补包 | 用 `update` 增量加一个 macOS 元素，见第 3 问 |

**第 3 问：后续要给某个平台补一个包，是新建还是更新？**

**答：更新（`POST /user/admin/software/update`），不要新建软件。给该平台新增一条 release，同时把该平台旧的置为非在架（`status=0`）；已发布的历史 `file_url` 不能改写。**

| 步骤 | 动作 |
|---|---|
| 1 | 调 `update`，`id` = 已有软件 ID，`platforms` **只传要补的那个平台**（增量语义，见 3.3） |
| 2 | 后端该平台插入新 release（`status=1`），并把该平台原有在架 release 置 `status=0` |
| 3 | 其它平台**保持不动**（这就是 update 采用「增量」而不是「整体替换」的原因） |
| 4 | 历史行**只改 `status`，不改 `file_url`**：已发出去的链接用户可能还存着，改了就成了「死链」且无法追溯 |

> 为什么不能改历史 `file_url`：已经有人下载过的链接是「对外承诺」，改了等于撕承诺；正确做法是**新增一行**，旧的留档。

**第 4 问：同一软件不同平台版本号不同怎么办？**

**答：允许不一致，版本号跟着每个 platform 条目走。**

| 项 | 规则 |
|---|---|
| 请求 | `platforms[].version` 每个平台各写各的；没写的回退到顶层 `version` |
| 示例 | Windows `1.0.2`、macOS `1.0.0`、Linux `0.9.0` **完全合法** |
| 商城卡片大字版本号 | 显示**主平台**（`platforms[0]`）的版本，或显示「1.0.2 / 1.0.0 / 0.9.0」这种并列（前端按空间选） |
| 详情页 | 每个平台各显示自己的版本号，不强行统一 |
| 后端校验 | **不做「所有平台版本必须相同」的校验**，那会把正常的迭代节奏卡死 |

**第 5 问：多平台提交，限流按 1 次算还是按 3 次算？**

**答：按 1 次算。** 一次 `create` 请求 = 1 次，不因为里面装了 3 个平台就算 3 次；否则「一个链接三个平台」反而比「分三次上传」更容易被限流，不合理。

**第 6 问：用户投稿也可以三平台同链接吗？**

**答：可以，`submit` 本来就是 `platforms` 数组**（3.6）。用户同样能一次勾三个平台、填同一个网盘链接；审核粒度见 3.9.1（**整条审**）。

**第 7 问：前端如果只传了 `platform` 单数，会不会被当成「只有一个平台」而丢掉另外两个？**

**答：不会丢，因为前端只在「只勾了 1 个平台」时才传单数。** 契约上是：前端勾了 ≥2 个平台 → 传 `platforms`；勾了 1 个平台 → 传 `platforms`（推荐）或 `platform`（兼容）。后端两种都认，**同时传时以 `platforms` 为准**（3.2 优先级表）。

### 3.13 接入指南专用查询（v3 新增）

> **站长的要求原话**：「接入指南里只应该对应 AI(Agent) 那个分类，因为那是用来指引客户下载 AI 工具台的。」
> 本节把「接入指南怎么取软件」定成契约，避免以后再出现「后台直传的软件跑进接入指南」。

#### ① 结论先说

| 问题 | 结论 |
|---|---|
| 接入指南要用的数据从哪来？ | **复用 `POST /user/software/list`，带 `category_id` = AI(Agent) 分类的 id**，不要另开新接口 |
| 分类 id 能写死成 `1` 吗？ | ❌ **不要写死**。见 ② |
| 前端现在怎么做的？ | ✅ **已按「先拉分类列表、按名字匹配」实现**（源码 `chatgpt-web/src/pages/guide/index.tsx` 的 `pickAgentCategoryId()`），与本节约定的做法一致 |
| 匹配不到怎么办？ | 退回「不筛选」并保留 GitHub Releases 兜底入口，**宁可多显示一个，也不让客户看不到下载入口** |

#### ② 为什么不要硬编码 `category_id = 1`

| 原因 | 说明（站长视角） |
|---|---|
| id 是数据库自增的 | 换环境、重建库、导入导出，id 都可能变。今天 `AI(Agent)` 是 `1`，明天重装数据库可能变成 `5` |
| 写死会「静默变空」 | 一旦 id 变了，接入指南的下载列表**整块消失且不报错**，最难排查 |
| 现场就有反例 | 实测 `category/list` 里 `效率软件` 是 `id=3`、`AI(Agent)软件` 是 `id=1`。**顺序并不按直觉**，说明 id 不能靠猜 |
| 名字比 id 稳定 | 分类名是站长自己填的，改动少；即使改名，也只是「匹配不上 → 退回不过滤」，不会白屏 |

#### ③ 契约（前后端都照此做）

| 项 | 约定 |
|---|---|
| 分类识别方式 | 前端先调 `POST /user/software/category/list`，**按名字匹配**含 `AI`（正则 `/AI\s*\(?\s*Agent/i`，兜底 `/^\s*AI/i`）的那条，取其 `id` |
| 分类名规范 | 后端/站长**请保持分类名为 `AI(Agent)软件`**（半角括号）。若必须改名，**提前告知前端**，否则会匹配不上并退回「显示全部」 |
| 取软件 | `POST /user/software/list`，body：`{"category_id": <上一步的 id>, "page":1, "page_num":6}` |
| 排序 | 前端会按名字把 Claude-haha 排最前、Codex 次之（见源码），后端无需特殊处理 |
| 返回条数 | 建议 ≤ 6 条（接入指南是「紧凑列表」，多了会挤） |
| `status` / `is_delete` | 只返回 `status=1`、`is_delete=0` 的（与商城公开列表一致） |
| `source` | **仍必须返回**（3.4 附），接入指南当前不按 `source` 过滤，但契约上不能缺 |
| 分类 id 变了怎么办 | 前端每次进页面都**重新拉分类列表**（不缓存 id），所以后端改 id **不需要通知前端改代码** |

**建议的请求示例**

```bash
# 第 1 步：拿分类，找出 AI(Agent) 的 id
curl -s -X POST 'https://www.rabbitj.top/apiAI/user/software/category/list' \
  -H 'Content-Type: application/json' -d '{}' | jq

# 第 2 步：用拿到的 id 取「接入指南要展示的客户端」（示例里 id=1，实际请用第 1 步的值）
curl -s -X POST 'https://www.rabbitj.top/apiAI/user/software/list' \
  -H 'Content-Type: application/json' \
  -d '{"category_id":1,"page":1,"page_num":6}' | jq
```

**验收判据**：第 2 步返回的**每一条**记录，其 `category_name` 都应是 `AI(Agent)软件`；若出现「效率软件」等其它分类，说明 `category_id` 筛选失效（见 3.4.1 ③ 的校验 SQL）。

#### ④ 需要后端确认的点

| # | 待确认 | 影响 | 建议 |
|---|---|---|---|
| 1 | **AI(Agent) 分类的 id 在线上是否稳定**（现在是 `1`）？后续会不会被重排/重建？ | 决定前端「按名字匹配」是否够用 | 保持按名字匹配即可；**后端承诺「分类 id 不随业务调整而变」更好** |
| 2 | `category/list` 是否支持按 `status` 过滤（只返回启用的分类）？ | 停用的分类若被匹配到，接入指南会取到空列表 | 建议 `category/list` 默认只返回 `status=1` 且 `is_delete=0` |
| 3 | 「AI(Agent)软件」这个名字**是否允许改名**？ | 改名会让正则匹配不上 → 退回显示全部 | 建议**这个名字固定**，要加分类就新增，不要改名 |
| 4 | 接入指南是否需要**排除某些软件**（如已下线的）？ | 目前靠 `status=1` 过滤，够了 | 不需要额外参数 |

## 四、文件上传专项

### 4.1 大小限制

| 类型 | 上限 | 理由 |
|---|---|---|
| 安装包 | **200MB** | 契约钉死；Nginx `client_max_body_size` 要同步调到 `210m`，否则 413 是 Nginx 先返回的 |
| 封面 | 5MB | 前端已压缩到 ≤180KB，给余量 |
| 单用户总配额（若开放用户上传） | 500MB | 防止变成免费网盘 |

### 4.2 类型白名单

| 平台 | 允许扩展名 | 允许 MIME（参考） |
|---|---|---|
| Windows | `.exe` `.zip` `.msi` | `application/octet-stream`、`application/x-msdownload`、`application/zip` |
| macOS | `.dmg` `.zip` `.pkg` | `application/x-apple-diskimage`、`application/zip` |
| Linux | `.AppImage` `.deb` `.tar.gz` `.zip` | `application/octet-stream`、`application/x-deb`、`application/gzip` |
| 封面 | `.png` `.jpg` `.jpeg` `.webp` `.svg` | `image/*` |

**校验要两道**：
1. 看扩展名（快速挡掉）；
2. 读文件头 **magic number**（前 4–8 字节）确认真实类型——扩展名可以随便改，文件头骗不了。

> `.svg` 特别提醒：SVG 能内嵌 `<script>`，如果直接当图片返回且同源，会变成 XSS。建议**封面不接受 SVG**，或统一走独立域名 + `Content-Disposition: attachment`。

### 4.3 病毒扫描与哈希校验（建议）

| 措施 | 做法 | 优先级 |
|---|---|---|
| SHA-256 哈希 | 上传时计算并入库（`file_hash`），商城详情页展示，用户可核对 | **高**（成本低、价值高） |
| 病毒扫描 | `ClamAV` 异步扫，扫完前 `status=0`，扫到毒自动下架并通知管理员 | 中（有服务器资源再做） |
| 大小/类型不合规 | 上传阶段直接拒 | **高** |
| 压缩包炸弹 | 限制 `.zip` 解压后总大小（若做在线解压） | 低 |

> 生活化：哈希值就像「文件的指纹」，同一个文件算出来一定一样。用户下载后自己算一遍，对得上就说明文件没被掉包。

### 4.4 对象存储与直链签名

建议：
1. **存对象存储**（OSS/COS/S3 兼容），不要存服务器本地磁盘——本地磁盘会满、不好备份、迁移麻烦。
2. **路径规则**：`software/{yyyy}/{mm}/{uuid}/{清洗后的文件名}`，**不要用用户原始文件名直接拼路径**。
3. **直链两种方式**：
   - 公开读（安装包本身不敏感）→ 直接给 CDN 地址，最简单；
   - 私有 + 签名 URL → `?Expires=...&Signature=...`，**有效期建议 ≥ 24h**，否则用户复制链接过一会儿就失效。
4. **下载计数**：如果走 CDN 直链，后端收不到下载请求。两个办法：`GET /user/software/download?id=` 做 302 跳转并 `download_count+1`，或让 CDN 日志回流统计。**建议前者**（实现简单，还能顺便做限流）。

### 4.5 防路径穿越（必须做）

用户传的文件名可能包含 `../../etc/passwd` 这种"往上跳目录"的写法，处理不当能把文件写到系统目录。

**规则**：
1. **永不**把用户文件名当路径用；落盘名用 `uuid` + 白名单扩展名。
2. 原始文件名只存数据库字段（`file_name`），展示时再读。
3. 如果必须用原文件名：去掉 `/` `\` `:` `*` `?` `"` `<` `>` `|`、去掉 `..`、去掉开头 `.`、限制长度 ≤ 100。
4. 存储路径拼接后用 `realpath()` 校验，确认结果仍在目标目录内。

### 4.6 防止把 upload 当免费图床

| 风险 | 措施 |
|---|---|
| 拿上传接口当图床外链 | 只允许白名单扩展名；封面单独 `kind=cover`，且**不允许公开直接访问**（走 CDN 防盗链） |
| 刷容量 | 单用户总量配额 500MB + 每日次数上限 |
| 刷请求 | 管理员 30 次/小时；普通用户 5 次/天；超限 `429` |
| 上传后不引用 | 定时任务清理「上传 7 天未被任何记录引用」的孤儿文件 |
| 滥用带宽 | CDN 限速/防盗链（Referer 白名单） |

### 5.2 `software_release`（版本/平台明细）

```sql
CREATE TABLE IF NOT EXISTS `software_release` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `software_id` BIGINT UNSIGNED NOT NULL COMMENT '关联 software.id',
  `platform` ENUM('windows','macos','linux') NOT NULL COMMENT '平台',
  `version` VARCHAR(50) NOT NULL COMMENT '版本号，如1.0.0',
  `file_url` VARCHAR(1000) NOT NULL COMMENT '安装包直链（或网盘链接）',
  `file_size` BIGINT UNSIGNED NULL DEFAULT NULL COMMENT '字节数',
  `file_hash` CHAR(64) NULL DEFAULT NULL COMMENT 'SHA-256',
  `changelog` TEXT NULL COMMENT '该版本更新说明',
  `review_status` ENUM('pending','approved','rejected') NOT NULL DEFAULT 'pending'
    COMMENT '版本级审核状态；官方为approved',
  `status` TINYINT NOT NULL DEFAULT 0 COMMENT '1=上架 0=下架',
  `download_count` INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '该版本下载次数',
  `insert_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `reviewed_at` DATETIME NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_sw_platform` (`software_id`, `platform`, `review_status`),
  KEY `idx_created` (`insert_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='软件版本/平台明细';
```

**「同项目同平台只允许一个已上架版本」的唯一约束**

MySQL 没有「条件唯一索引」直接写法，二选一：

**方案 A（推荐，最稳）**：加一个生成列，只对「在架」行取 `platform`，其他为 `NULL`（MySQL 唯一索引允许多个 NULL）。

```sql
ALTER TABLE `software_release`
  ADD COLUMN `active_platform` ENUM('windows','macos','linux')
    GENERATED ALWAYS AS (
      CASE WHEN `status` = 1 AND `review_status` = 'approved' THEN `platform` ELSE NULL END
    ) STORED COMMENT '在架平台，用于唯一约束',
  ADD UNIQUE KEY `uk_sw_active_platform` (`software_id`, `active_platform`);
```

**方案 B（兼容 MySQL 5.7 / 不支持生成列时）**：在代码里用事务保证——审核通过前 `SELECT ... FOR UPDATE` 查该 `(software_id, platform)` 是否有在架版本，有就先把旧的置 `status=0`；同时加普通索引 `idx_sw_platform` 兜底性能。

> 说明：`open_source_project` 用的是「旧的置为 archived」思路，这里改成 `status=0`，语义等价。

### 5.3 `software_upload`（上传记录表）

作用：每次上传都留一条记录，方便查「谁传的、多大、传了多少次、有没有被引用」，也是限流配额的数据来源。

```sql
CREATE TABLE IF NOT EXISTS `software_upload` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '上传者用户ID',
  `kind` ENUM('package','cover') NOT NULL COMMENT '类型',
  `file_name` VARCHAR(255) NOT NULL COMMENT '原始文件名（已清洗）',
  `file_url` VARCHAR(1000) NOT NULL COMMENT '存储地址',
  `file_size` BIGINT UNSIGNED NOT NULL COMMENT '字节数',
  `file_hash` CHAR(64) NULL DEFAULT NULL COMMENT 'SHA-256',
  `mime_type` VARCHAR(100) NULL DEFAULT NULL,
  `ip` VARCHAR(45) NULL DEFAULT NULL COMMENT '上传IP（IPv6最长45）',
  `user_agent` VARCHAR(500) NULL DEFAULT NULL,
  `ref_software_id` BIGINT UNSIGNED NULL DEFAULT NULL
    COMMENT '被哪条软件引用；NULL=孤儿文件，可定时清理',
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '1=有效 0=已清理',
  `insert_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user_time` (`user_id`, `insert_time`),
  KEY `idx_ref` (`ref_software_id`),
  KEY `idx_hash` (`file_hash`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='软件上传记录';
```

### 5.5 多平台数据模型：方案 A vs 方案 B（v2 新增）

> ✅ **2026-10-25 站长已拍板：现有线上 `software` 表是「单平台」结构**（一个平台一行），多平台改造走**方案 A**（新增 `software_release` 子表），不做方案 B（拆三行）。
> 这条决定解决了本文原「待确认第 1 条」这个唯一阻塞项；`software_release` 的建表 SQL 见 5.2，迁移顺序见 7.4。
> 另外两条也已定：**后端先支持单平台、`platforms[]` 随后升级**（前端已做降级，不会白屏）；**审核粒度按「整条审」**（一次通过，所有平台一起上架）。

> 背景：v1 的 5.2 已经设计了 `software_release` 子表，但**现有线上 `software` 表到底是一行一个平台、还是一行一个软件**，我无法从仓库确认（见待确认清单第 1 条）。下面把两条路彻底比清楚。

**方案 A（推荐）：`software` 主表存软件本体，`software_release` 按 (software_id, platform) 存每个平台的包与链接**

| 项 | 内容 |
|---|---|
| 表结构 | `software` 1 行 = 1 个软件（名称、简介、封面、来源、审核状态、排序）；`software_release` N 行 = N 个平台（`platform`、`version`、`file_url`、`file_size`、`status`、`download_count`） |
| 一软件三平台 | `software` 1 行 + `software_release` 3 行（`file_url` 可相同） |
| 唯一约束 | `(software_id, platform, status=1)` —— 实现方式见 5.2 的生成列 `uk_sw_active_platform`（MySQL 不支持条件唯一索引，用 `active_platform` 生成列把非在架行置 `NULL`，唯一索引允许多 NULL） |
| 商城列表 | 主表分页 1 次 + release 批量查 1 次（`WHERE software_id IN (...)`），组装 `platforms[]`，**不会出现重复卡片** |
| 下载统计 | 天然分平台（`software_release.download_count`），软件级 `software.download_count` 存合计 |
| 改造成本 | 需要建 `software_release`（5.2 已给 DDL）+ 写接口按数组拆行 + 读接口组装数组；**现有单平台数据要迁一次**（把 `software.platform/file_url/file_size/version` 搬成一条 release） |
| 风险 | 迁移脚本写错会丢链接 → **必须先备份 + 先跑 `SELECT` 核对条数再 `INSERT`** |
| 适合 | 官方软件也要多平台、要分平台统计、以后要按平台补包 —— **就是本站当前需求** |

**方案 B（不推荐）：不改表，一次提交拆成三条 `software` 记录（同一 `name` 不同 `platform`）**

| 项 | 内容 |
|---|---|
| 表结构 | 不新建子表；三平台 = `software` 表三行，`name` 相同、`platform` 不同 |
| 一软件三平台 | `software` 3 行（三行 name 一模一样） |
| 唯一约束 | 现有 `(name, platform)` 之类即可（具体看现有表，**待确认**） |
| 商城列表 | **会显示三张重复卡片**（同一软件出现三次），必须让列表接口**按 `name` 聚合**成一条，再把三行的平台合成 `platforms[]` → 聚合逻辑复杂且易错（同名不同软件怎么办？大小写/空格差异？用户和官方同名？） |
| 下载统计 | 分平台容易（每行一个平台），但「这个软件总下载量」要 `SUM` 三行 |
| 改造成本 | 表面「不改表」，实际把复杂度全推给**读接口聚合 + 编辑接口联动**（改简介要改三行、下架要下三行、删除要删三行，容易漏） |
| 风险 | ① 三张重复卡片（站长一眼就会问「怎么有三个一样的」）；② 改名要同步三行；③ 聚合靠 `name` 字符串匹配，**不可靠**（改名/空格/大小写都能拆散）；④ 一条投稿审核要审三行，驳回原因说不清 |
| 适合 | 完全不想动数据库、且能接受商城显示三条 —— **不满足本站需求** |

**对比结论**

| 维度 | 方案 A（子表） | 方案 B（拆三行） |
|---|---|---|
| 商城卡片 | ✅ 一条，天然不重复 | ❌ 三条，必须靠 `name` 聚合 |
| 改简介/改名 | ✅ 改一行 | ❌ 要改三行，漏改就不一致 |
| 下架/删除 | ✅ 主表一次 + release 批量 | ❌ 要操作三行 |
| 分平台下载统计 | ✅ 原生 | ⚠️ 可以但合计要 SUM |
| 按平台补包 | ✅ 插一条 release | ⚠️ 要找到对应那一行 |
| 按平台审核 | ✅ 5.2 已留 `review_status` 字段 | ❌ 天然三行三审，但队列里是三条 |
| 改造成本（一次性） | 中（建表 + 迁数据） | 低（不改表） |
| 长期维护成本 | **低** | **高**（聚合逻辑与联动到处补） |
| 本项目推荐 | ✅ **A** | ❌ 不推荐 |

> **结论：采用方案 A。** 方案 B 省下的只是「建一张表」的一次性成本，代价是**长期在列表聚合、编辑联动、审核粒度上反复打补丁**，而且「三张重复卡片」是站长验收时一定会提的问题。
> **前置动作**：先按待确认清单第 1 条跑一条 SQL，确认现有 `software` 表结构；若现有表已有 `software_release`，方案 A 属于「把已有子表用起来」，成本更低。

### 6.2 硬性安全规则

1. **管理员角色由后端判断**，不能信前端传的 `role` 字段，也不能只看「有没有登录」。
2. **用户只能改自己的**：`update` / 重新提交时，若 `author_user_id != 当前用户` 一律 **403**（管理员除外）。`my-submissions` 必须按 `author_user_id` 过滤。
3. **驳回原因长度**：1–500 字，超长截断或 422；为空则拒绝（`reject` 必须给理由，否则用户不知道改什么）。
4. **XSS 防护**：
   - `name`、`summary`、`changelog`、`reviewer_note` 全部按**纯文本**存和返回，前端只用文本节点渲染；
   - 若前端需要富文本，必须由后端白名单过滤（`<b> <i> <a> <br> <p>` 之外全删），**不接受 `<script>`、`<iframe>`、`on*=` 事件属性**；
   - `repo_url`、`file_url` 只接受 `http://` / `https://` 开头，**拒绝 `javascript:`、`data:`**（`data:` 只允许 `cover_url` 的图片前缀）。
5. **文件名注入**：见 4.5；另外展示文件名时做 HTML 转义，避免文件名里的 `<` 破坏页面。
6. **SQL 注入**：全部用参数化查询/ORM，不拼字符串。
7. **越权下载**：`pending`/`rejected` 的软件，其 `file_url` 不应在公开接口返回；如果需要，走签名 URL 短期有效。
8. **敏感信息不外泄**：审核列表里不要返回用户的手机号、邮箱等无关字段，只返回 `author_name`。

## 七、与现有系统的兼容与迁移

### 7.1 字段变更：增量还是破坏性？

| 接口 | 变更 | 是否破坏 | 前端兼容处理 |
|---|---|---|---|
| `/user/software/list` | 新增 `source`、`keyword` 参数 | **否**（都是可选） | 不传就是不筛 |
| `/user/software/list` | 返回项新增 `source/author_name/version/download_count/review_status` | **否**（加字段） | 老前端忽略新字段 |
| `/user/software/list` | **v2：返回项新增 `platforms[]`** | **否**（加字段） | 老前端忽略新字段；新前端多平台渲染，无该字段时降级（见 3.4） |
| `/user/admin/software/create` | 新增 `source/version/changelog` | **否** | 不传就按官方默认 |
| `/user/admin/software/create` | **v2：新增 `platforms[]`；`platform` 降为兼容期可选** | **否**（`platform` 仍被接受） | 老前端只传 `platform` → 服务端按单元素数组处理，行为不变（见 3.2 优先级表） |
| `/user/admin/software/update` | 同上 + `is_delete`（原本就有） | **否** | 局部更新 |
| `file_size` 语义 | 旧值可能是 `"12.4 MB"` 字符串，新值建议字节数 | **可能** | 前端统一成一个格式化函数：数字按字节格式化，字符串原样显示。**后端不要中途改老数据**，前端已兼容两种 |

**结论：全部是增量变更，没有破坏性变更。** 唯一需要小心的是 `file_size` 的类型混用，已在上面处理。

**v2 补充（多平台）**：
- **`platforms[]` 是纯新增字段**，老前端不传不影响；老前端传 `platform` 也照旧能用，**双向兼容**。
- **`platform` / `file_url` 的语义在 v2 降级为「主平台摘要」**，但**字段名、类型、含义都没有变**（仍是最主要那个平台的平台与链接），所以老前端显示不会错——只是老前端只能看到第一个平台。**这不是破坏性变更，是能力增强**。
- **真正需要动数据的是「表结构」**（方案 A 迁 release，见 5.5），那属于后端迁移，**不是接口破坏**；迁移期间接口可先只返回单数 `platform`，前端按 3.4 降级表正常显示。

### 7.2 老数据 `source` 默认值

```sql
-- 建议：存量全部官方（因为此前能进后台的，都是我们自己录的）
UPDATE `software` SET `source` = 'official' WHERE `source` IS NULL OR `source` = '';

-- 存量审核状态默认通过，避免突然从商城消失
UPDATE `software` SET `review_status` = 'approved' WHERE `review_status` IS NULL;

-- author_name 补齐
UPDATE `software` SET `author_name` = 'anyGPT 官方'
WHERE (`author_name` IS NULL OR `author_name` = '') AND `source` = 'official';
```

> 为什么默认 `official`：如果默认成 `user` + `pending`，站长一上线就会发现**整个商城空了**（全在待审）。默认官方 = 老软件照常显示，风险最小。
> 顺序很重要：**先 `ALTER` 加字段（带默认值），再跑上面 UPDATE，最后再考虑收紧默认值**。
