## 二、P1（必做）· 后台删除留言接口

### 现状

后台「留言」页现在有三个动作：隐藏、回复、**删除**。
「隐藏」是老接口（`is_delete: true` 标记，数据还在、还能恢复）；
「删除」是 2026-10-24 新加的，站长原话是「留言给我一个删除的按钮，后台的，不然删不掉」——要的是**真正从库里删掉**。

前端已经写好并接上了，但后端接口不存在：

```
POST /apiAI/user/admin/feedback/delete   →  404 {"detail":"Not Found"}
```

（作为对照，同样方式请求一个我编的假路径 `/user/zzz_missing`，返回的也是 `{"detail":"Not Found"}`，两边完全一致，所以这个 404 是真没有，不是权限问题。）

### 要实现的

**接口**：`POST /user/admin/feedback/delete`

**请求体**：

```json
{ "id": 14 }
```

**成功返回**（和现有接口格式保持一致）：

```json
{ "code": 0, "codeMsg": "已删除" }
```

**失败返回**：

```json
{ "code": 4003, "codeMsg": "仅管理员可操作" }
{ "code": 4005, "codeMsg": "留言不存在或已删除" }
```

**要做的校验**（顺序建议）：

1. 登录有效，且 `is_staff` 为真 → 否则 `4003`；
2. `id` 存在 → 否则 `4005`；
3. 真正 `DELETE` 掉这行数据。

### 两个可选实现方式

- **物理删除**（推荐，符合站长“删不掉”的原意）：`DELETE FROM feedback WHERE id = ?`
- **软删除**：如果担心误删想留证据，把 `is_delete` 置真，同时**从后台列表的默认查询里排除**——但注意：现在的「隐藏」已经是这个效果了，如果删除也这么做，站长会分不清两个按钮的区别。所以推荐物理删除。

### 参考：现有留言接口的字段

`POST /user/admin/feedback`（列表）返回的每条记录长这样，删除接口按 `id` 定位即可：

```json
{
  "id": 14,
  "content": "【发票申请】{...}",
  "is_read": false,
  "is_delete": false,
  "reply": null,
  "created_at": "2026-10-22 14:00:00"
}
```

## 三、P2（必做）· 合并开票：`/user/invoice/create` 支持多笔

### 需求背景

站长要求：「点开发票时增加多选，可以选多个充值记录合并开票，金额自动相加」。

前端已经完整实现：勾选模式、最多 20 笔、合计金额按分累加、弹窗里逐笔明细可核对、已开票/审核中的订单不可勾选。
**唯一卡点在后端**：`/user/invoice/create` 目前只接受一笔。

### 前端现在传什么（关键，照这个实现就对了）

合并提交时，前端会**同时**传两个字段：

```json
{
  "bill_id": "1791363073531,1791363073532,1791363073533",
  "bill_ids": ["1791363073531", "1791363073532", "1791363073533"],
  "amount": 300.0,
  "order_no": "1791363073531,1791363073532,1791363073533",
  "title_type": "company",
  "title": "上海某某科技有限公司",
  "tax_no": "91310000000000000X",
  "email": "boss@example.com",
  "remark": "抬头和上次一样",
  "userId": 132,
  "userName": "钱镜如"
}
```

**为什么要同时传两种**（这不是前端偷懒，是为了兼容）：

- `bill_ids`（数组）：**新后端读这个**，能准确知道要合并哪几笔；
- `bill_id`（逗号串）：老后端只读字符串，至少能解析出「一个订单号」，不会因为字段类型从 string 变 array 就把整条请求判为非法。

单笔开票时**不传** `bill_ids`，`bill_id` 就是普通的一笔订单号——所以你的单笔逻辑完全不用改。

### 后端要改的逻辑

```
1. 取参加合并的订单列表：
   优先读 bill_ids（数组，非空时以它为准）
   没有该字段或为空 → 退回读 bill_id（单个字符串 = 单笔，行为与现在完全一致）

2. 逐笔校验（任何一笔不合格，整单拒绝，不要部分成功）：
   - 订单存在且属于当前用户        → 否则 4005「找不到这笔订单，请刷新支付记录」
   - 订单已支付且是充值订单        → 否则 4007「只有已支付的充值订单可以开票」
   - 该订单没有 pending/issuing/issued 的发票 → 否则 4006「订单 xxx 已开过发票」
   - 抬头、税号、邮箱合法          → 否则 4008

3. 金额由后端重算，绝不信前端传的 amount：
   amount = Σ(每笔订单的 pay)

4. 落库：
   - 一笔订单一行发票明细（推荐，便于以后单笔退款/冲红）
   - 用 invoice_id 或 batch_id 把这些行标记成「同一张票」
   - 状态统一 pending
```

### 数据模型建议（两种都行）

**方案 A：一票多单，明细表**（推荐）

```sql
-- 主表
invoice (id, user_id, amount, title_type, title, tax_no, email, remark,
         status, invoice_no, reject_reason, created_at, updated_at)

-- 明细表：一张票对多笔订单
invoice_item (id, invoice_id, bill_id, amount)
-- 唯一约束：user_id + bill_id 只能出现在一张有效状态的票里
```

**方案 B：不加表，把多单拼在现有 `bill_id` 字段里**

把 `bill_id` 存成逗号串（如 `"B1,B2,B3"`），金额仍由后端按串里的订单汇总。
改动最小，但**「一单一票」的唯一约束要靠代码校验**，查询“这笔订单开过票没”也麻烦一些。如果时间紧可以先这样，后续再迁 A。

### 唯一约束怎么加（重要）

「一单一票」这条规则对合并同样成立。建议：

```sql
-- 方案 A 下，在 invoice_item 上加联合唯一索引
CREATE UNIQUE INDEX uk_invoice_item ON invoice_item (user_id, bill_id);
```

> 注意 `rejected`（已驳回）的票**不算开出**，用户要能重新申请。所以：
> 驳回时要么删掉对应的 `invoice_item` 行、要么不要把 rejected 的行算进唯一约束
> （比如唯一索引只建在有效状态上，或在代码里用事务判断，别硬用数据库唯一键卡死）。

### 实际会看到的现象（给站长自测用）

- **接口没升级时**：用户勾 3 笔点提交 → 后端返回 `4005找不到这笔订单` 或 `4008`；
  前端会弹一句很明确的话：
  「如果反复失败，说明后端暂不支持合并开票，请把这几笔订单号发给站长手动处理，或改成一笔一笔单独开票。」
  这个提示是故意写长的，就是为了让用户别反复点。
- **升级成功后**：提示「已提交 3 笔合并开票申请，合计 ¥300.00，请等待站长审核」，
  后台审核列表里能看到这条（金额是合计）。

### 实测证据（为什么确定现在不支持）

我用站长账号真实 token 打 `/user/invoice/create`，做了一组对照：

| 我发的内容 | 后端返回 | 说明 |
|---|---|---|
| 什么都不传 | `4008 请从支付记录里选择订单开票` | 基准 |
| **只传 `bill_ids` 数组** | `4008 请从支付记录里选择订单开票` | **和什么都不传一模一样 → 说明 `bill_ids` 被完全忽略** |
| 传逗号串 `bill_id` | `4005 找不到这笔订单` | 把整串当成一个订单号去查了 |

第二行是关键：如果后端读了 `bill_ids`，它至少会去校验数组里的订单，从而报 `4005`（订单不存在）；但结果和空请求一样，证明这个字段根本没被读取。

## 八、给前端留的兼容说明（站长不用管）

同理，删除接口上线而前端未部署时，旧前端没有「删除」按钮，不会调用它，无副作用。
