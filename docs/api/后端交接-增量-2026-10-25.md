## 二、P5（必做）· `source` 字段缺失

### 现象

商城有「官方软件 / 用户上传」两个页签。前端按 `source` 字段分流，但线上接口**根本不返回这个字段**，所以「官方软件」页签永远是空的。

### 实测证据

```
POST /user/software/list   body {"page":1,"page_num":50}
→ code "0"，total 4，返回 4 条
→ 单条记录字段共 13 个：
   id, category_id, category_name, name, summary, cover_url, version,
   links, sort, status, insert_time, update_time, is_delete
→ 'source' in record === false      ← 就是这一行
```

13 个字段里**没有 `source`**，不是值的问题，是字段压根不存在。

### 要实现的

`/user/software/list` 与 `/user/software/detail` 的每条记录都加上：

```json
{ "source": "official" }
```

**取值只有两个**：`official`（官方）、`user`（用户上传）。

`source` 语义见 v3 文档第 2.1 节，这里只强调两条：

1. **服务端生成，不接受前端传**：管理员 `create` 一律写 `official`，用户 `submit` 一律写 `user`；
2. **存量回填**：现有 4 条（id 1–4）都是站长手录的，按 v3 文档第十节第 2 条，全部回填 `official`。

### 验收

```bash
curl -s -X POST 'https://www.rabbitj.top/apiAI/user/software/list' \
  -H 'Content-Type: application/json' -d '{"page":1,"page_num":20}' \
  | python3 -c "import sys,json;d=json.load(sys.stdin);print([r.get('source') for r in d['list']])"
# 期望：[ 'official', 'official', 'official', 'official' ]
# 现在：[ None, None, None, None ]
```

> 前端对 `source` 缺失**已做兜底**（`normalizeRecord` 会补默认值），所以页面不会崩，只是页签分不对——**这也是为什么这个 bug 不显眼但必须修**。

## 三、P7（补文档）· 后台分类 3 个接口

> 这三个接口前端**早就在用**（`src/request/api.ts:514-555`），但 v3 文档只写了 `category/list`（公开的），后台的增删改**一个字都没写**。
> 下面是按前端真实调用反推的契约，参数和返回都是前端实际发的，不是设计的。

### 3 个接口一览

| 接口 | 方法 | 作用 | 前端位置 |
|---|---|---|---|
| `/user/admin/software/category` | POST | 分类列表（分页） | `getAdminSoftwareCategories` |
| `/user/admin/software/category/create` | POST | 新建分类 | `createAdminSoftwareCategory` |
| `/user/admin/software/category/update` | POST | 编辑 / 上下线 / 删除 | `updateAdminSoftwareCategory` |

**注意：没有单独的 delete 接口。** 删除 = 调 `update` 传 `is_delete: true`（软删除）。这点必须写清，否则后端容易多做一个 `/delete` 出来。

### P7-1 `POST /user/admin/software/category`（列表）

**请求**：

```json
{ "page": 1, "page_num": 10 }
```

**成功返回**（沿用现有格式，**与公开 `category/list` 一致**）：

```json
{
  "code": "0",
  "codeMsg": "成功",
  "list": [
    {
      "id": 3,
      "name": "效率软件",
      "sort": 1,
      "status": 1,
      "insert_time": "2026-10-25 11:09:04",
      "update_time": "2026-10-25 11:09:18",
      "is_delete": false
    },
    {
      "id": 1,
      "name": "AI(Agent)软件",
      "sort": 0,
      "status": 1,
      "insert_time": "2026-10-01 15:32:53",
      "update_time": "2026-10-01 15:32:53",
      "is_delete": false
    }
  ],
  "total": 2,
  "page": 1
}
```

> 上面这段是**公开接口 `category/list` 的真实返回**（2026-10-25 实测，未带 token 即可访问）。
> 后台列表接口前端按同一结构解析（`payload.list` / `payload.total` / `payload.page`），**后端若返回结构不同，后台分类面板会空白**。

**字段说明**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | number | `1` = 上线，`0` = 下线。公告面板据此显示「已上线/已下线」 |
| `sort` | number | 排序值，小的在前 |
| `is_delete` | boolean | 软删除标记，列表默认**不要**返回已删除的 |
| `insert_time` / `update_time` | string | `YYYY-MM-DD HH:mm:ss` |

### P7-2 `POST /user/admin/software/category/create`（新建）

**请求**：

```json
{ "name": "开发工具", "status": 1, "sort": 0 }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 分类名，前端已 `trim()`，后端仍需校验非空、判重 |
| `status` | 否 | 默认 `1`（新建即上线） |
| `sort` | 否 | 默认 `0` |

**成功返回**：

```json
{ "code": "0", "codeMsg": "成功" }
```

> 前端判断成功用的是 `res?.data?.code === '0' || res?.code === 0`（`saved()` 函数，`src/pages/admin/software/index.tsx:124`），
> **注意它同时接受字符串 `"0"` 和数字 `0`** —— 所以后端返回哪种都行，但**同一套接口内请保持一致**。

### P7-3 `POST /user/admin/software/category/update`（编辑 / 上下线 / 删除）

**一个接口三种用法**，靠传哪些字段区分：

**① 编辑名称/排序/状态**

```json
{ "id": 3, "name": "效率软件", "status": 1, "sort": 1 }
```

**② 只切上下线**（前端「上线/下线」按钮）

```json
{ "id": 3, "status": 0 }
```

**③ 删除**（软删除，前端「删除」按钮）

```json
{ "id": 3, "is_delete": true }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | **是** | 定位记录；缺失应返回参数错误 |
| `name` / `status` / `sort` | 否 | **局部更新**：没传的字段保持原值，不要重置 |
| `is_delete` | 否 | 传 `true` 即软删除 |

**⚠️ 最容易做错的一点：`update` 必须是局部更新。**

前端「删除」时**只传 `{id, is_delete}`**，不带 `name`/`status`/`sort`。
如果后端按「整行覆盖」实现，会把 `name` 写成空、`status` 写成 0——**分类名就没了**。
请按「传了才改，没传不动」实现。

**成功返回**：

```json
{ "code": "0", "codeMsg": "已删除" }
```

`codeMsg` 前端会直接弹出来当提示语（`res?.data?.codeMsg || '保存成功'`），所以建议按动作给不同文案：新建/编辑给「保存成功」，删除给「已删除」。

### 分类删除的业务规则（建议）

- 分类下**还有软件**时，建议**拒绝删除**并返回明确提示（如 `code 4009, codeMsg "该分类下还有 N 个软件，请先移走"`），避免软件变成「无分类孤儿」；
- 若后端希望「删分类 = 软件一并下架」，也可以，但**必须告知前端**，因为前端弹窗文案需要配合改。

> 当前前端**没有做这个拦截**，会直接发删除请求。所以这条规则要么后端挡住，要么就不挡，别两边都以为对方在挡。

## 四、P6（说明）· 响应包格式：其实不是阻塞项

v3 文档 3.0.1 把「响应格式不统一」列为**最大联调障碍**。**这个判断偏重了**，需要更正：

### 前端拦截器已经自动兼容两种格式

`src/request/index.ts:69-77`：

```ts
let data: ResponseData<T> = await response.json()
if (!isResponseData(data)) {
  data = {
    code: response.status === 200 ? 0 : response.status,
    data: (data as any)?.data ? (data as any).data : data,
    message: ''
  }
}
```

`isResponseData()` 只认「同时有 `code` + `data` + `message`」这一种形状。线上返回的是顶层 `list`（没有 `data`），所以**走进兼容分支**：把整个响应体塞进 `data` 字段。

于是商城代码里 `res.data.list` 和 `res.data.data` 都能取到数据（`src/request/software.ts:421` 两种都试了）：

```ts
const list = (payload.list || payload.data || []) as SoftwareRecord[]
```

### 结论

| 方案 | 后端成本 | 前端要不要改 |
|---|---|---|
| **A. 保持现状**（顶层 `list` + 字符串 `code`） | 0 | 不用，已兼容 |
| **B. 改成 `{code:0, data:{...}, message:"ok"}`** | 全站接口改造 | 不用，两种都吃 |

**建议 B 但不必急**：新接口按约定格式写，老接口不用专门回去改。**这不该挡商城上线**。

## 五、已实测确认的事实（省得后端再试）

这 5 条都是 2026-10-25 晚直连线上跑出来的，可以直接采信：

| # | 事实 | 证据 |
|---|---|---|
| 1 | `page_num` 上限 **50**，超了返回 **422**（不是业务错误码） | 传 100 → `{"detail":[{"type":"less_than_equal","msg":"Input should be less than or equal to 50"}]}` |
| 2 | `page_num=50` 正常 | 返回 `code "0"`、`total 4`、4 条记录 |
| 3 | `category/list` 公开可访问（不带 token） | 直接返回 2 条分类 |
| 4 | 后台接口（含 `admin/*`）不带 token 一律 `3004 用户状态已过期` | 连不存在的假路径 `/user/zzz_nope_404` 也返回 `3004` → **说明鉴权在路由之前，不能用 401/404 判断接口是否存在** |
| 5 | `detail?id=1` 需要登录 | 不带 token → `3004` |

> 第 4 条是个**排查陷阱**，值得单独记：这个站不带 token 时，**所有** `/user/*` 都返回 `3004`，
> 所以「接口不存在」和「没权限」无法从响应里区分。要验证接口是否存在，**必须带有效 token**。
